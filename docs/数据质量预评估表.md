## 一、评估方法

| 维度 | 定义 | 判定方式 | 对应 SQL 手段 |
|---|---|---|---|
| **完整性** Completeness | 关键字段是否存在空值 | 空值行数 / 总行数 | `IS NULL`、`TRIM(x)=''` |
| **唯一性** Uniqueness | 主键/业务键是否唯一 | 重复多余行数 = 总行数 − 去重后行数 | `COUNT(*) - COUNT(DISTINCT pk)` |
| **有效性** Validity | 枚举取值是否在合法集合内 | 非法取值行数 / 总行数 | `NOT IN (...)`、`LOWER(TRIM(x))` |
| **一致性** Consistency | 同义字段格式是否统一 | 非标准格式行数 / 总行数 | `RLIKE` 正则、`REGEXP_REPLACE` |
| **准确性** Accuracy | 数值是否在业务合理区间 | 越界行数 / 总行数 | `CAST` + 区间判断 |

> 说明 1：问题占比 `bad_ratio` 统一保留 4 位小数，即 `bad_cnt * 1.0 / total_cnt`。
> 说明 2：结论栏判定口径 —— **问题行数 = 0 记「通过」；> 0 记「不通过」**，并在括号内标注处理周次。

## 五、结论

**数据整体可用性判断**：6 张表中 `ods_store` 五维度全通过，可直接作为门店维表使用；
`ods_user_behavior` 与 `ods_order_item` 结构干净，仅时间格式与数量字段需处理，清洗成本低；
`ods_product` 需修正 11 行日期缺失与 56 行价格逻辑异常；
**`ods_order` 是质量最差且最关键的一张表**，重复率 3.85%、渠道写法混乱率 48.61%，
不经清洗直接统计会让 GMV 与订单量同时失真，必须先处理。

**本周已解决的核心问题**：完成缺失值与重复值两类清洗。
`dwd_order` 从 15,600 行去重到 15,000 行，order_id 重复归零，订单量指标恢复真实；
`dwd_user.age` 空值与越界全部归零、`dwd_product.launch_date` 空值归零，
使**订单量、GMV、用户年龄段分布**三项核心指标具备了可用性，
预计订单量口径的可信度从「虚高约 4%」提升到准确。

**遗留风险**：金额异常（925 行）、枚举中英文与大小写混用（18,650 行）、
日期格式不统一（8,115 行）、`quantity` 异常（1,081 行）这四类问题尚未处理，
其中枚举混用会持续破坏渠道与状态维度的分组统计，是下一周最高优先的处理项；
金额异常若不修复，客单价与 GMV 仍会存在约 6% 的偏差。

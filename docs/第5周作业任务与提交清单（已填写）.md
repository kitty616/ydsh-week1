## 一、本周任务详细化

第 5 周不再新增功能，而是把前四周的成果**整合成可交付、可复现、可展示的完整项目**：
先端到端跑通并逐层对账，再把散落在各周的过程记录沉淀成五份规范文档，
然后审查 Git 历史、写英文 README、做答辩材料，最后复盘。

### 子任务 1：全流程整合与联调（3 课时）

**任务目标**：原始 CSV → ODS → 清洗 → DWD → DWS → ADS → 预测 → NL2SQL → 可视化 → 部署，端到端跑通并逐层对账。

**操作步骤**：
① 写 `python/verify_e2e.py`，把核对做成 67 条可复现断言，分 9 个环节（S1–S9）；
② 每条断言的期望值必须有来源——上游层重算，或前四周文档里已登记的值，不凭记忆写常量；
③ FAIL 与 WARN 分开：口径不一致必须改，耗时波动只记录；
④ 发现问题当场修，修完重跑，直到 0 FAIL。

**关键决策**：核对脚本**只读**。跑多少遍结果一致，不写任何业务表，可以直接改成 CI 任务。

**产出物**：`python/verify_e2e.py`、`data/e2e_result.json`、`docs/第5周_端到端联调报告.md`、`docs/第5周_端到端联调_原始输出.md`。

**验收标准**：各层行数与指标值逻辑自洽，全流程可一键复现。
**实测**：**64 项通过 / 0 项失败 / 3 项告警**，30.6 秒跑完；GMV 在 7 个位置同值 36,116,687.06。
**联调抓到 3 个真问题并全部修复**：
① `dws_category_day` 比全站少 349,609.57 元（0.97%）——139 笔订单明细被整单清洗后，
inner join 把整笔吃掉，改为 UNION ALL 单列「未知品类」；
② 分组取整再相加累积 0.13 元舍入漂移——存储层不再取整，保留可加性；
③ `app` 服务漏注入 `MYSQL_ROOT_PASSWORD`，三引擎对账连不上——已补齐，仍走 `${VAR:?}` 语法。

④ 每份文档末尾必须有「变更记录」和「遗留问题」，不允许只写成绩。

**产出物**：`docs/项目文档/01_需求文档.md`、`02_数据质量清洗报告.md`、`03_架构设计文档.md`、`04_部署手册.md`、`05_API配置指南.md`（同时提供 docx）。

**验收标准**：五份文档结构统一、内容完整、可追溯。

### 子任务 3：Git 提交历史审查（1 课时）

**任务目标**：检查提交网络图、分支结构、约定式提交、PR/Issue 留痕，确认无敏感信息泄露。

**操作步骤**：
① `git log --oneline --graph --all` 看整体形态；
② 统计提交类型分布，列出不规范的提交及原因；
③ 检查分支命名与合并方式，已合并分支是否清理；
④ 扫描敏感信息：`git grep` + `git log -p --all -S`；
⑤ 本周工作全部走 `feature/week5-integration` 分支，`--no-ff` 合并，让合并节点在图上可见。

**产出物**：`docs/第5周_Git审查报告.md`。

**验收标准**：主干历史清晰、分支命名规范、PR/Issue 记录完整、无敏感信息泄露。
**实测**：见审查报告，问题项已列整改人与整改时间。

**实测**：README 英文版 12 个章节、含架构 ASCII 图与 3 张真实截图；PPT 16 页，

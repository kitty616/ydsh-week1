## 一、链路总览

```
自然语言问题
    ↓
Schema 注入（21 张表、字段 + 中文语义，6,067 字符）
    ↓
大模型生成 SQL（Prompt 含 21 条硬约束 + 6 个 few-shot + 选表指南）
    ↓
静态校验器  ←—— 这一步是整个链路的安全底线
    ├─ 只允许单条 SELECT / WITH
    ├─ 拦截 DDL / DML 关键字
    ├─ 表名白名单（21 张，先排除 CTE 名）
    ├─ 别名识别（AS 定义的名字不算列）
    ├─ 列归属核对（列属不属于这张表）
    ├─ 日期/省名等值 → 前缀匹配（静默空兜底）
    ├─ 自动补库名（按真实所属库）
    ├─ 改写后二次复核
    └─ 自动加 LIMIT
    ↓
beeline 执行（Docker 内 Hive 4.0.0）
    ↓
结果表
```

## 二、Schema 抽取

### 2.1 为什么不用 pyhive

部署手册给的示例是 `pyhive`。实测在 Windows + Python 3.13 下装不上：`pyhive` 依赖的 `sasl` 需要 C 编译环境，`pip install` 直接失败。

改用 **beeline**（Hive 自带客户端）执行 `DESCRIBE` 抽取结构，效果等价，且不引入额外依赖。这是"手册给的路走不通时换一条"的正常工程决策，不是偷懒。

后四张 ADS 表是 4.7 补的：原来是 14 张，地域/渠道/门店排名这几类问题没有对应的成品表可查，模型只能把维度列硬挂在汇总表上。

最后三张维表（`dim_pay_type` / `dim_order_status` / `dim_user`）是 4.8 补的，起因很直接：规则 13 里早就写着「province 在 dim_user 里」，可 `dim_user` 根本没在设计清单里——**Prompt 自相矛盾，模型照着规则去 JOIN，被白名单拦下**。支付方式和订单状态同理，不 JOIN 维表就只能给用户看 PT01、OS04。

### 2.3 为什么只暴露 21 张表

Hive 里实际有 47 张表，包括 `dwd_order_clean`、`dq_compare` 这类中间表和质检表。全部塞给模型有两个坏处：

1. **Prompt 变长**，成本上升、注意力被稀释；
2. **选错表概率上升**——模型看到 `dwd_order` 和 `dwd_order_clean` 两个名字，很可能选错。

所以只给「分析时真正该用的 21 张」，中间表干脆不出现在 Prompt 里。这是**用白名单做负向约束**：模型看不到，就选不错。

反过来也有代价：**该给的没给全，模型就会硬编**。4.7 那次 10004 就是这个原因——地域成品表被挡在门外，模型只能给汇总表加 `province`。白名单要按「问题类型」覆盖全，不是越少越好。

### 2.4 为什么还要手工补业务语义

Hive metastore 里的字段注释是中文的，但在容器 locale 下 `DESCRIBE` 输出会变成 `????????`（编码问题）。而字段名本身对大模型信息量不足：`status_code` 到底是订单状态还是商品状态？`mom_rate` 是环比还是同比？

所以采用「**结构自动抽 + 语义人工补**」：字段名和类型由脚本从 Hive 拉，中文含义在 `schema_extract.py` 的 `TABLE_META` 字典里维护。

这样做的另一个好处是：语义字典是**版本可控的**，改了可以 diff；而数据库注释改了没人知道。

## 三、Prompt 设计

### 3.1 十条硬约束

| # | 约束 | 防止什么问题 |
|---|---|---|
| 1 | 只输出一条 SELECT | 模型爱写解释文字，破坏下游解析 |
| 2 | 严禁写操作 | 模型可能生成 DELETE / DROP |
| 3 | 表名必须带库名前缀 | Hive 里裸表名会解析到 default 库 |
| 4 | 日期字段是字符串，不要猜格式 | 模型爱套 `to_date()` / `str_to_date()`，Hive 语法不同 |
| 5 | 优先 ADS → DWS → DWD | 防止动辄去 join 明细表，慢且易错 |
| 6 | 标识符用反引号、字符串用单引号、**禁用双引号**；列名不加库名 | 模型会写成 `AS "华东GMV"`，Hive 把双引号内容当字符串，别名位置直接语法错误 |
| 7 | 结果要排序、必要时 LIMIT | 无序返回对用户无意义 |
| 8 | 「销售额」默认指 gmv | 消除业务词与字段名的歧义 |
| 9 | 相对时间以**数据最新日期**为基准换算，禁用 `current_date()` | 数仓是 2024 年快照，用当天日期做条件永远落在空区间，聚合结果是 NULL 而不是报错 |
| 10 | 只输出用户问的指标列；用了聚合就必须把所有非聚合列写进 GROUP BY | Hive 不做隐式分组推断，漏写直接 `SemanticException 10025` |

第 4 条是踩过坑才加的：Hive 的日期函数和 MySQL 差异很大，`to_date()` 在 Hive 里接受多种格式但跨版本行为不一致，让模型自由发挥等于给自己埋雷。

第 9、10 条是**接上真实模型之后**才补的。前面没有 Key 的几周里，规则模式生成的 SQL 都是手写的、必然合规，这两类问题根本暴露不出来——它们不是模型不听话，而是 Prompt 没交代清楚数据的"物理事实"（数据是什么时候的、字段值长什么样）。详细过程见 5.5 节。

### 3.2 Few-shot 的选择

只放两个例子，一简一繁：

- 简单：`2024 年 6 月的总 GMV → SELECT ... WHERE month='2024-06'`，示范「月份字段是字符串」。
- 带排序：`销量最高的前 5 个品类 → SELECT ... WHERE rank_no <= 5 ORDER BY rank_no`，示范「优先用 ADS 成品表」。

例子多了反而有害：模型会倾向于模仿例子的表层句式，而不是理解规则。

### 3.3 一个未采用的方案

考虑过让模型先输出「思考过程」再输出 SQL（Chain-of-Thought）。放弃了，原因：

- 增加了 token 成本；
- 输出解析变复杂（要分离思考和 SQL）；
- 对这类「单表查询 + 固定 Schema」的问题，规则约束比思考链更有效。

如果问题复杂到需要多表 join + 子查询，才值得上 CoT。

## 四、SQL 静态校验器

### 4.1 为什么必须有

大模型生成的 SQL 有两类典型失败：

- **语法/语义错**：表名编造、字段不存在 → 执行报错，可接受；
- **危险操作**：生成 `DELETE` / `DROP` / 多语句注入 → 直接改坏数据，不可接受。

第二类必须靠校验器拦，不能指望 Prompt。Prompt 是"请求"，校验器是"强制"。

### 4.2 校验规则

```python
DANGEROUS = re.compile(r"\b(insert|update|delete|drop|alter|create|truncate|load|grant|revoke|merge|overwrite)\b", re.I)
```

| 检查项 | 实现 |
|---|---|
| 写操作拦截 | 正则匹配 12 个危险关键字 |
| 语句类型 | 必须以 `SELECT` / `WITH` 开头 |
| 多语句 | `;` 数量 > 1 即拒绝 |
| 表名白名单 | 抓 `FROM` / `JOIN` 后的标识符，比对 21 张表；CTE 名先排除（4.8） |
| 自动补库名 | 裸表名按**真实所属库**补全（`dws_*`→`ydsh_dws`、`dwd_*`/`dim_*`→`ydsh_dwd`、`ads_*`→`ydsh_ads`） |
| 改写后复核 | 补全后重新抓表名再验一遍白名单，防止改写本身制造新错误 |
| 中文列名纠偏 | 注释里的中文被当列名时，按「注释→英文列名」唯一映射改回（4.6） |
| 列归属核对 | 列存在但不在本次 FROM/JOIN 的表里 → 拦，并指出它只在哪张表（4.7） |
| 别名识别 | `AS xxx` 定义的名字算合法标识符，`ORDER BY` 引用别名不误拦（4.8） |
| 时间范围一致性 | 问句无时间词、SQL 却加了日期过滤 → 拦，避免答案静默缩水（4.8） |
| 日期等值兜底 | `dt = '2024-06'` → `dt LIKE '2024-06%'`；`year = '2024'` → `month LIKE '2024-%'`（4.7） |
| 省名等值兜底 | `province = '浙江'` → `province LIKE '%浙江%'`（列里存的是「浙江省」）（4.7） |
| 注释剥离 | 执行前去掉 `--` 与 `/* */`，避免压平换行时注释吞掉后续 SQL |
| 自动加 LIMIT | 无 `LIMIT` 时追加 `LIMIT 200` |

### 4.4 Code Review 发现的问题与修复

PR #2 提交后做了一轮自查式 Review，发现校验器本身 4 个缺陷。全部实测复现后修复，过程记录在 PR 的 5 条行内评论里。

| 级别 | 问题 | 后果 | 修复 |
|---|---|---|---|
| Blocker | 裸表名一律补 `ydsh_ads.` | `dws_trade_day`→`ydsh_ads.dws_trade_day`，表不存在却返回 `ok=True`，放行了必然失败的 SQL | 白名单改为 `表名→全名` 映射，按真实库补全；补全后二次复核 |
| Major | 测试只断言 `ok` 布尔值 | 上述 Blocker 显示 PASS 被漏掉——用例里恰好用了 `dws_trade_day`，但没人检查它被改写成什么 | 用例增加期望 SQL 字段，判定同时校验 `expect_sql in fixed` |
| Major | 执行前把 `\n` 换成空格 | `-- 注释` 后的 `WHERE` / `LIMIT` 被整体注释掉，**查询不报错但返回全表** | 新增 `strip_comments()`，先剥注释再压平 |
| Minor | `call_llm` 无异常兜底 | 有 Key 时网络抖动直接抛栈，不回落规则模式 | `try/except` 返回 `(None, 错误摘要)`；模式标注「模型调用失败，已降级」 |

Blocker 的实测证据（修复前）：

```
输入: SELECT * FROM dwd_order
输出: SELECT * FROM ydsh_ads.dwd_order    ← 库名错
ok = True                                  ← 校验放行
```

修复后同一输入得到 `ydsh_dwd.dwd_order`，并新增 4 条用例锁住这个行为。

这个教训比代码本身更重要：**校验器的价值在于「拦住错误」，一旦它自己动手改写却不受检验，它的「通过」反而是风险来源。**

### 4.5 校验器拦不住什么

必须说清楚边界，否则会有虚假安全感：

> 4.6 / 4.7 / 4.8 之后，「列名不存在」「列挂错表」「问句被擅自加时间条件」已经不在盲区里了——校验器会拦下并附真实列名。下面三条仍然拦不住。

1. **合法但算错的 SQL**：比如把 `SUM(pay_amount)` 写成 `SUM(discount_amount)`，语法没问题、表名在白名单内，校验器放行。这类只能靠人工核对结果。
2. **性能问题**：全表扫描 34 万行的笛卡尔积也能通过校验，只是跑很久。
3. **语义歧义**：「销售额」到底指 GMV 还是净收入、按用户省份还是门店省份，校验器判断不了（4.7 口径那节就是例子）。

所以校验器是**安全网，不是正确性保证**。

### 4.6 中文列名幻觉：一次真实的执行期报错

第 5 周演示环境联调时，页面上问「销量最高的前 5 个品类」，执行失败：

```
Error while compiling statement: FAILED: SemanticException [Error 10004]:
Line 3:6 Invalid table alias or column reference '排名'
```

模型生成的是：

```sql
SELECT `一级品类`, `该品类全年GMV`, `占全站GMV比重`
FROM `ydsh_ads`.`ads_category_topn`
WHERE `排名` <= 5 ORDER BY `排名`
```

**四个中文标识符全部来自 schema 注释**，表里根本没有这些列：

| 模型写的 | 真实列名 | 注释原文 |
|---|---|---|
| `排名` | `rank_no` | 排名，1 为最高 |
| `一级品类` | `category` | 一级品类名称 |
| `该品类全年GMV` | `gmv` | 该品类全年 GMV（元） |
| `占全站GMV比重` | `gmv_share` | 占全站 GMV 比重（小数） |

三个根因叠在一起：

1. **Prompt 自己给了错误暗示。** 原规则 6 写的是「标识符（含中文列别名）用反引号包裹，如 `AS 华东GMV`」——这句话在教模型「中文可以出现在反引号里」，却没说「只能出现在 AS 之后」。
2. **校验器只查表名，不查列名。** 4.2 的规则里表名有白名单，列名完全没有核对，所以这条 SQL 静态校验**放行**了，错误拖到 Hive 编译期才暴露。
3. **自修复拿不到有用信息。** 报错只说 `'排名'` 不存在，没说正确列名是什么；模型第二次仍然在猜中文名，`已自修复 1 次` 之后照样失败。

修复分三层，缺一层都还会复发：

| 层 | 改动 | 作用 |
|---|---|---|
| Prompt | 规则 6 重写；新增规则 12，直接给出「对/错」对照；schema 注入时加一行「英文名才是列名，`//` 后是解释」 | 从源头降低发生率 |
| 静态校验 | 新增 `fix_cn_columns()`：从 schema 注释构建「中文说明 → 英文列名」映射，能唯一对上的直接替换，对不上的判为错误 | 拦住，而不是放行 |
| 报错信息 | 列名错误时附上该表真实列名清单 | 让自修复一次改对 |

中文映射的归一化规则（实测命中率最高）：去括号内容、去逗号后的解释、去空格。
`该品类全年 GMV（元）` → `该品类全年GMV` 与模型输出完全一致；`一级品类名称` 用前缀匹配接住模型省掉的「名称」。

**不能过度纠偏**，所以加了三道刹车：

- 只接受**全局唯一**的中文映射，同一中文对应多个列就丢弃（宁可报错，不猜）；
- `AS` 之后的中文是合法别名，不替换；
- 先剥注释、再遮蔽单引号字符串，避免把 `WHERE category = '一级品类'` 误判成列名。

回归结果（6 条边界用例）：

| 用例 | 结果 |
|---|---|
| 截图原样的中文列名 | ✅ 自动改为 `category, gmv, gmv_share, rank_no` |
| 无反引号的中文列名 | ✅ 同样纠正 |
| `排名 AS 名次` 混写 | ✅ 改为 `rank_no AS 名次` |
| 合法中文别名 `AS 一级品类` | ✅ 原样保留 |
| 字符串常量含中文 | ✅ 不误判 |
| 真正不存在的列（销售额、利润） | ✅ 拒绝并列出真实列名 |

线上 5 条测试问题重跑 **5/5 通过**，含最容易诱发中文列名的「品类销量的排名和金额，按排名排序」。

顺手修掉的两个隐患：

- **注释里的中文会被当列名**：`-- 按排名 排序` 会误报，现在先 `strip_comments()` 再校验；
- **注释里的危险词会误杀**：`-- 不要 delete 数据` 会触发 `DANGEROUS` 拦截，同一次修改一并解决。

> 这次的教训不是「模型不行」，而是**校验器的检查范围要和 Prompt 的约束范围对齐**：Prompt 管住了列名，校验器却只查表名，等于留了一个不设防的口子。

### 4.7 跨表串列：列名对了、表挂错了

4.6 修完之后，演示环境里换了个问法又崩了：

> 广东省的销售额是多少

```
Error 10004: Line 3:6 Invalid table alias or column reference 'province'
```

```sql
SELECT SUM(gmv) AS total_sales
FROM ydsh_dws.dws_trade_day
WHERE province LIKE '%广东省%'
```

`province` **是真实存在的列**，只是不在 `dws_trade_day` 里（在 `dim_store`、`ads_region_sales`、`ads_store_rank` 里）。所以 4.6 那套「中文列名」检查完全放行，表名也在白名单里，静态校验一路绿灯，错误再次拖到 Hive 编译期。

这次不是模型在编列名，是**它不知道地域该去哪张表**。查下去发现两个洞：

**洞一：Prompt 只暴露了 14 张表，地域那张成品表不在里面。**

数仓实际落了 47 张表，`schema_extract.py` 只向模型暴露 14 张，`ads_region_sales`（省份销售分布）、`ads_store_rank`（门店排名）、`ads_channel_sales`（渠道分布）、`ads_kpi_overview`（指标宽表）四张 ADS 成品表全在门外。模型面对的处境是：知道要按省过滤，但看得到的表里没有任何一张有 `province`，只能硬往汇总表上加。

这不是模型幻觉，是**上下文供给不全**。补表之后，同一句话一次就对：

```sql
SELECT province, gmv, gmv_ratio
FROM ydsh_ads.ads_region_sales
WHERE province LIKE '%广东%'
-- 广东省 | 2,254,505.49 | 6.24%
```

**洞二：校验器只核对「列名存不存在」，不核对「列属不属于这张表」。**

于是补了 `check_column_refs()`，三条判定，只抓确定的错：

| 判定 | 例子 | 处理 |
|---|---|---|
| 限定列（别名.列） | `s.city`、`ydsh_dws.dws_trade_day.store_id` | 前缀解析到表后，核对该表有没有这一列 |
| 裸列名 | `WHERE province …` | 列在数仓里存在、但不在本次 FROM/JOIN 的表里 → 拦 |
| 字符串比较左值 | `WHERE year = '2024'` | 不在任何表里 → 判为凭空造列，拦 |

报错信息带上「它只在哪张表」，自修复才有方向：

```
列不在本次查询的表里：province 不属于 ydsh_dws.dws_trade_day
（它只在 ads_region_sales、ads_store_rank、dim_store）。
按省份汇总直接用 ydsh_ads.ads_region_sales；按城市 / 门店用
dws_store_day JOIN dim_store。当前表真实列名 → …
```

**踩到的坑：别名把关键字吃了。** 第一版解析 `FROM a JOIN b ON …` 时，正则把 `JOIN` 当成 `a` 的别名吃掉，`b` 根本没进表清单，于是 `b` 的列全被判成「不属于本次查询」——误报比漏报更糟，正确 SQL 被拦死。修法是别名位加负向先行断言，把 `join/where/on/group/order/…` 排除在外。这条写进了单元用例，因为它在真实 SQL 里几乎必然复现。

#### 顺带发现的三种「静默错」

同一个问句换几次措辞，又暴露三类错：

| 现象 | 生成的 SQL | 后果 | 处理 |
|---|---|---|---|
| 月份筛在日粒度列上 | `WHERE dt = '2024-06'` | 语法对、执行成功、**0 行** | 校验层改写为 `dt LIKE '2024-06%'` |
| 凭空造年份列 | `WHERE year = '2024'` | 10004 报错 | 表里有 `month` 没有 `year` 时，改写为 `month LIKE '2024-%'` |
| 省名等值匹配 | `WHERE province = '浙江'` | 列里存的是「浙江省」，**0 行** | 去「省/市」后缀改 `LIKE '%浙江%'` |

三处都是**确定性改写**，不依赖模型重试：语义唯一、不需要猜。这是本轮的一个判断——Prompt 管得住「大多数」，管不住「每一次」；凡是能唯一确定的错法，就在校验层改掉，而不是反复劝模型。

#### 弱模型上，示例比规则管用

本机 `.env` 只配了智谱，`llm_provider` 解析出来是 `glm-4-flash`。这个模型对文字的服从度明显弱于对示例的服从度，实测（`temperature=0`，同一句问话连跑三次结果完全一致，说明不是随机抖动）：

| Prompt 变体 | 「广东省的销售额」 | 「每个城市卖了多少」 |
|---|---|---|
| 只有规则 13（地域只在某几张表） | ❌ 仍挂 `dws_trade_day` | ❌ 仍挂 `dws_trade_day` |
| 规则 + 一条省份示例 | ✅ | ❌ |
| 规则 + 省份示例 + 城市示例（城市在最后） | ❌ 被最近的示例带偏 | ✅ |
| 规则 + 城市示例 + **两条省份示例**（过滤 + 排名） | ✅ | ✅ |

结论有两条：

1. **示例要成对给。** 只给「广东省」一条时，「按省份看销售额」会退回汇总表——模型把「汇总」理解成必须 `SUM + GROUP BY`；再补一条不带过滤的「各省份销售额排名」，等于告诉它「省份维度的答案本来就在这张表里」。
2. **示例顺序会影响结果。** 弱模型会把**紧挨着问题的那条示例当模板套**，所以省份示例放在最后，城市示例放在它前面。这个顺序是试出来的，不是拍出来的。

#### 口径：同一个问题有两个正确答案

补完表之后，「广东省的销售额」有两个都对的数：

| 口径 | 走哪张表 | 广东省 | 说明 |
|---|---|---|---|
| 用户所在省份 | `ads_region_sales` | **2,254,505.49**（891 单） | 消费者在哪；15 省合计 = 全站 GMV |
| 门店所在省份 | `dws_store_day` JOIN `dim_store` | 581,858.32（222 单） | 门店开在哪 |

两者不矛盾，是两种业务视角。系统默认取**用户口径**，理由是经营大屏的省份分布图用的就是 `ads_region_sales`——同一个人在大屏和问答里看到同一个省，不该是两个数。

顺带把规则兜底 `rule_based()` 里的省份分支也改成 `ads_region_sales`：原先是 JOIN `dim_store` 走门店口径。不改的话，一旦演示时模型调不通降级到规则模式，同一句问话会给出 581,858.32，和模型模式的 2,254,505.49 并排出现——现场没法解释。

#### 回归结果

| 用例组 | 内容 | 结果 |
|---|---|---|
| 内置测试集 | 6 条典型问题（含广东省） | **6/6** 执行成功 |
| 地域/维度组 | 广东省、按省份看销售额、哪个省份最好、每个城市、广东进前 15 门店、浙江省 GMV | **6/6**，首轮命中 5 条，1 条自修复 1 次后成功 |
| 边界用例（离线） | 跨表串列、凭空造列、别名吃关键字、合法 JOIN、中文列名混写 | **12/12** 判定正确，无误拦 |
| 随机问法 | 6 条口语化提问（哪个品类最赚钱、6 月比 5 月涨多少等） | **6/6** 执行成功 |

`verify_e2e.py` 同步复跑：**67 项断言 64 PASS / 0 FAIL / 3 WARN，31.8 秒**，八处 GMV 仍全部收敛到 36,116,687.06。

> 这轮的教训和 4.6 是一条：**模型答不对，先看供给够不够，再看校验严不严，最后才怪模型。** 4.6 是「列名没给对」，4.7 是「表没给全」——两次都是上下文问题伪装成模型问题。

### 4.8 反向翻车：校验器把正确的 SQL 拦了

4.7 之后校验器能拦「列挂错表」了，但同一个机制很快把对的也拦了。

#### 现象

问「各支付方式的成交额占比」，模型给出的 SQL：

```sql
SELECT pay_type_code,
       SUM(pay_amount) AS total_gmv,
       SUM(pay_amount) / SUM(SUM(pay_amount)) OVER () AS gmv_ratio
FROM ydsh_dwd.dwd_order
GROUP BY pay_type_code
ORDER BY gmv_ratio DESC
```

页面报：`gmv_ratio 不属于 ydsh_dwd.dwd_order（它只在 ads_channel_sales、ads_region_sales）`，
后面还跟着一句「只能用列出来的真实列名，不要自己造字段」。

先不急着改 Prompt——把这条 SQL 直接丢给 Hive 跑一遍：**跑通了**，4 行结果，
微信支付 9,668,087.14 占 26.77%。SQL 是对的，是校验器错了。

#### 根因

`gmv_ratio` 是 SELECT 里 `AS` 现定义的**别名**，`ORDER BY` 引用别名是标准写法。
但 `check_column_refs` 只认识「表里的列」：裸标识符里出现 `gmv_ratio`，
既不是列、也不是表名或关键字，可它偏偏是**别的表里的真列**（`ads_region_sales.gmv_ratio`），
于是正好落进 4.7 刚写的判定条件——「列存在，但不在本次查询的表里」——被判成串列。

一句话：**4.7 的规则没有区分「列」和「别名」。**

#### 修复

加 `collect_aliases()`：把 `AS xxx` 定义的名字全部收进合法标识符集合，再做列归属核对。
`CAST(x AS DECIMAL(18,2))` 里的 `AS` 后面是类型，`decimal / int / bigint` 本就在 `SQL_NOISE` 里，
天然被挡掉，不会误收成别名。

顺带发现同类误拦：**CTE**。

```sql
WITH m AS (SELECT dt, SUM(gmv) AS g FROM ydsh_dws.dws_trade_day GROUP BY dt)
SELECT dt, g FROM m ORDER BY g DESC
```

`m` 是语句里临时定义的表，不在 21 张白名单里，于是报「引用了白名单外的表：m」，
改完库名又报一次「库名补全后仍不在白名单：m」。表名白名单也得先认出 CTE，
`WITH a AS (` 和 `, b AS (` 两种位置都要抓。

#### 从「拦对」里捡出的三个静默错

改完别名，30 条回归过了 29 条。剩下那条和对的 SQL 摆在一起看，反倒暴露了三个
**不报错、但答案是错的**问题：

| 现象 | 错在哪 | 补的规则 |
|---|---|---|
| 问「取消了多少订单」，自修复一轮后 SQL 多了 `WHERE dt LIKE '2024-06%'` | 问句没提月份，答案从全年 2,023 单缩成 6 月的 159 单，页面照样写「执行完成」 | 规则 14 + 校验器新增 `check_time_scope`：问句无时间词却出现日期过滤 → 拦 |
| 问「门店经营情况」写成 `SUM(d.aov)` | aov 是客单价均值，相加得出 948,527 元/单 | 规则 21：比率/均值列不能 SUM，客单价重算 `SUM(gmv)/SUM(order_cnt)` |
| 问「6 月各品类卖了多少」，SQL 没 `GROUP BY` | 出来 248 行（每天×每品类），用户要 9 行（一品类一行） | 规则 19 + 三张日粒度表在 schema 描述里注明「日粒度，要汇总就 GROUP BY 维度」 |

第二个尤其典型：**数字大得离谱却不报错**，比报错难查得多。修完 948,527 变 2,478.63，
和 `dws_store_day` 的 gmv ÷ order_cnt 对得上。

#### 收尾：把「不误拦」变成可回归的

`test_guard.py` 从 17 条扩到 35 条，新增的主体不是更多攻击样本，而是**正例**：

- 窗口算占比 + `ORDER BY` 引用别名（本次事故原样）
- `CAST(... AS DECIMAL(18,2))` 里的 AS 不被当成别名
- CTE、子查询、`UNION ALL`、`CASE WHEN`、三表 JOIN
- 6 条「问句与时间条件是否一致」

原有 12 条负例（写操作、编造表、串列、造列）全部保留，且必须继续拦住。

> 这一轮的教训和前三次都不同：4.6 / 4.7 是「拦不住」，4.8 是「拦错了」。
> 校验器必须成对测——**负例证明它有牙，正例证明它不咬自己人**。
> 只测负例的校验器会越改越严，最后把正常提问全挡在门外，而单测还全绿。

### 5.5 接上真实模型后暴露的六类问题

规则模式下 SQL 是人手写的，必然合规；第一次让真模型写，一条「上周华东区的销售额是多少」连撞四个坑，换问题又撞两个。这是本周期信息量最大的一段——**「没有 Key」不只是少一个演示，而是少了一整类验证**。

| # | 现象 | 真实原因 | 修在哪 |
|---|---|---|---|
| 1 | `ParseException: cannot recognize input near 'AS' '"华东区上周GMV"'` | 模型用双引号包别名，Hive 把双引号当字符串字面量，不能当标识符 | Prompt 规则 6 + 校验器引号归一化 |
| 2 | `content` 空、`finish_reason=length`，被当成"模型没回答"而降级 | GLM-5.x 始终思考，思考内容也计入 `max_tokens`，实测吃掉 7,062 字 | `max_tokens` 800→4096，空正文单独报错 |
| 3 | `400 该模型始终思考，不支持关闭思考` | 思考档位字段是 `thinking.level`，不是 `thinking.type` | 探明形状后**最终选择不传参数**，用服务端默认档位（见下） |
| 4 | SQL 语法全对、校验全过，结果 `NULL` | 模型把「上周」按 `current_date` 算，而数仓是 2024 年快照 | 把数据区间注入 Schema Prompt + 规则 9 |
| 5 | 同上，结果 `NULL` | `province` 实际值是「上海市」「江苏省」，模型写 `IN ('上海','江苏')` 精确匹配 | 字段注释写明带后缀、用 `LIKE` |
| 6 | `SemanticException 10025: Expression not in GROUP BY key 'week_start'` | 模型多加了日期辅助列，又没写进 GROUP BY，Hive 不做隐式推断 | Prompt 规则 10 |

**逐条拆一下**，因为每条的错误类型都不一样：

**1. 双引号别名——语义没错，语法错了。** 模型生成的 `AS "华东区上周GMV"` 在 MySQL 里合法，在 Hive 里双引号是字符串字面量，写在别名位置就是语法错误。这类问题的特点是"看着完全正确"，只有真跑才炸。修法分两层：Prompt 里说清 Hive 的引号规则（预防），校验器里按 Hive 语义做归一化（兜底）——`AS "x"` 改成反引号，其余 `"x"` 改成单引号，两步都对应 Hive 的真实语义，不是模糊猜测。

**2. 空正文——最容易被误判的一条。** 第一次跑出 `模式：规则模式（模型调用失败，已降级：正文为空）`，看着像模型不行。实际是 `max_tokens=2048` 被思考内容整段吃光：`finish_reason=length`、`reasoning_content` 有 7,062 字、`content` 是空字符串。**思考型模型的 token 预算是"思考 + 正文"共用的**，这一点在 OpenAI 兼容协议里没有任何标记，只能靠实测发现。顺带把 ping 脚本的 `max_tokens` 从 50 提到 512，否则连"请回复收到"都返回空。

**3. 思考档位传参——报错信息会误导人。** 传 `{"type":"low"}` 返回 `400 该模型始终思考，不支持关闭思考；请使用 low、high 或 max`，看着像"low 不被接受"，其实是 `type` 这个字段本身只能填 enabled/disabled。正确形状是 `{"level":"low"}`。用原始 HTTP 把 6 种参数形状打了一遍才定位到：

| 参数形状 | 结果 |
|---|---|
| 不传 | ✅ 思考 415 字 |
| `thinking.type = low` | ❌ 400 |
| `thinking.level = low` | ✅ 思考 347 字 |
| `thinking = "low"` | ❌ JSON 反序列化失败 |
| `reasoning_effort = low` | ✅ 思考 238 字（另一条路径） |

> **后续修正（第 3 周末）**：上表是在「生成一条 SQL」这种短任务上测的，`level=low` 确实更短。但做 `ai_insight.py` 的摘要生成时发现规律反了——思考长度会撑满 `max_tokens` 上限，`level=low` 在同等预算下反而比不传参数想得更多（`max_tokens=1024` 时：不传 → 1,434 字且正文正常，`level=low` → 2,798 字且正文为空）。
> 所以 `llm_provider.py` 里给智谱配的 `extra_body` 已删除，统一用服务端默认档位。**参数的最优取法依赖任务形状，不能从短任务外推到长任务**——完整实测见《AI洞察报告》4.3 节。

**4 & 5. 两个 NULL——不报错的错，最难发现。** 第 4 条让模型用 `current_date` 去查 2024 年的数据，条件永远不成立；第 5 条让模型按 `IN ('上海')` 去匹配「上海市」。两条都通过了全部静态校验、执行也不报错，只有一个 NULL。这类问题的共同点是**错误信息为零**。修法是把数据的物理事实写进 Prompt：顶部注入「数据覆盖 2024-01-01 ~ 2024-12-31（历史快照）」，字段注释写明「省份全称，带省/市后缀」。

**6. GROUP BY——模型的通用 SQL 习惯与 Hive 的严格模式冲突。** 模型喜欢在结果里附一列日期范围"让答案更好看"，但 Hive 要求所有非聚合列都出现在 GROUP BY 里。这条只能靠 Prompt 约束，因为校验器很难静态判断（子查询带出的列算不算非聚合列，需要真正的语法树）。

**分类看，六条里只有 2 条会抛异常，另外 4 条是"静默错误"**：空正文被降级吞掉、NULL 结果、空集合。这恰好印证了 4.5 节那句话——校验器能拦语法和表名，拦不住"语义上正确、业务上错误"。真正的兜底是**换问题、换口径、换层级去对同一个数字**，也就是 5.2 节那两张独立核算表。

## 八、LangChain 编排版实现

### 8.1 为什么补这一版

任务书子任务 4 点名要求「用 LangChain 实现 NL2SQL」。第一版交付用的是 OpenAI SDK 直连 + 自写 Prompt + 自写校验，理由是链路只有「一次生成 + 一次校验」，框架会掩盖细节。

这个理由在工程上站得住，但它回答的是「我为什么那样做」，不是「任务书为什么那样要求」。评审看的是能不能按指定技术栈实现。所以补一个 LangChain 版，两版并存，用同一批问题对比——这比争论哪个更好更有说服力。

`python/nl2sql_chain.py`，与 `python/nl2sql.py` 共用同一个校验器、同一个执行器、同一份 Schema，只替换编排层。

### 8.2 编排方式的差异

| 环节 | 手写版 `nl2sql.py` | LangChain 版 `nl2sql_chain.py` |
|---|---|---|
| Prompt | 手工拼 `dict` 列表，few-shot 靠 append | `ChatPromptTemplate.from_messages`，声明式 |
| 输出解析 | 正则抽 ` ```sql ` 代码块 | `with_structured_output(SQLPlan)` + Pydantic 模型 |
| 降级 | `if/else` 判断有没有 Key | `Runnable.with_fallbacks` 三级自动降级 |
| 执行编排 | 顺序调用函数 | LCEL 管道 `prompt \| llm \| parse \| guard \| exec` |
| 链路可视化 | 无 | `chain.get_graph().draw_ascii()` 自动生成 |
| 耗时观测 | 无 | `BaseCallbackHandler` 逐步计时与 token 统计 |

结构化输出模型：

```python
class SQLPlan(BaseModel):
    sql: str = Field(description="单条 Hive SELECT 语句，不带结尾分号")
    tables_used: list[str] = Field(default_factory=list, description="引用到的完整表名")
    reasoning: str = Field(default="", description="一句话说明选表和聚合的理由")
```

手写版要靠正则从自然语言里抠 SQL，模型多说一句「以下是查询：」就得靠容错；结构化输出把这件事交给协议层，`Reasoning` 字段还顺带产出了可审计的选表理由。

### 8.3 三级降级：框架在这里确实省事

```
1. 结构化输出   prompt | llm.with_structured_output(SQLPlan)
        ↓ 模型不支持 function calling / json mode
2. 纯文本兜底   prompt | llm | StrOutputParser | 正则抽 SQL
        ↓ 无 Key / 网络不通 / 额度用尽
3. 规则兜底     rule_based()
```

代码只有一行：

```python
return primary.with_fallbacks([text_chain, rule_chain])
```

手写版要实现同等的三级降级，得三层嵌套 `try/except`，而且很容易漏掉某一层的异常类型。

一个刻意的设计：**没有 Key 时不让主链被绕开，而是让它真的抛异常，交给 fallback 接住**。这样「降级机制」每次运行都在被真实验证，不会等到真出事才发现 fallback 早就失效了。

### 8.3.1 自查发现的一个问题：模式标注会撒谎

第一版写完，我用「无效 Key」跑了一次，输出是这样的：

```
问题：用户价值分层结构是什么样的
模式：deepseek（3.6s）          ← 显示的是服务商名
生成 SQL：
SELECT user_segment, user_cnt, ... FROM ydsh_ads.ads_user_segment ...
```

SQL 实际来自规则链（三级降级全部走完了），但模式显示「deepseek」。**这正是本文档 5.2 节批评过的那件事——让规则结果冒充模型能力。**

原因：`mode` 是按「有没有配置 Key」推断的，不是按「实际命中了哪一级」。

第一次修法用了 `contextvars`：在每一级降级执行前 `set()` 一个层级名，`ask()` 里 `get()` 出来。结果读出来永远是初始值 `未执行`。原因是 **LangChain 的 `RunnableParallel` 在线程池里执行，`contextvars` 会被复制到子线程，子线程里的 `set()` 主线程读不到**。

正确修法是让层级作为**数据**在管道里流动，而不是作为外部状态：

```python
def _stage(runner, name):
    """把「这一级叫什么」写进输出"""
    return RunnablePassthrough.assign(
        sql=runner,
        stage=RunnableLambda(lambda _: name),
    )
```

三级降级各自打标，最终成功的那个把 `stage` 写进结果，`ask()` 直接读 `out["stage"]`。修复后：

```
模式：规则模式（未配置 API Key）              ← 无 Key
模式：deepseek 调用失败，已降级为规则模式      ← 有 Key 但 401
模式：deepseek（结构化输出）                  ← 正常（待配 Key 验证）
```

这个问题的价值在于：它和我批评的错误是同一个。写代码时想着「不能让规则结果冒充模型」，实现时却因为**判断依据选错**（用配置推断结果，而不是用实际执行路径）把同一个错误又犯了一遍。判断依据必须来自执行结果，不能来自执行前的假设。

记在这里，因为它比「一次跑通」更能说明问题。

### 8.5 A/B 实测结果

同一批 6 条问题，两条链路各跑一遍（`python python/nl2sql_chain.py --compare`）。跑了两轮，结论完全不同，都值得记录。

#### 8.5.1 第一轮：无 Key，规则模式

- 6/6 一致是"同一份规则，必然一样"，等于没测；
- 1/6 一致才是两条独立生成路径的真实表现：同一句话、两次采样，写法不同、结果都对。

差异的来源不是"谁更聪明"，而是**编排方式改变了生成分布**：LangChain 版要求模型先填 `{sql, tables_used, reasoning}` 三个字段，这个结构化任务本身就把注意力引向了"先选表、再解释"，所以两条都往上走 ADS 层；手写版直接吐 SQL，容易顺着"汇总"的直觉往 DWS 走。

所以"SQL 是否一致"不是一个好的评测指标——**文本比对只能发现写法差异，发现不了口径差异**。两个写法完全不同的 SQL 可能都对（这次就是），两个长得一样的 SQL 也可能都错（比如都误用 `current_date`）。真正要盯的是结果数字，而这一点只能靠对账，不能靠 diff。

### 8.7 什么时候用哪一版

| 场景 | 建议 | 理由 |
|---|---|---|
| 作业/评审，要求指定技术栈 | LangChain 版 | 按要求交付 |
| 自己调试 Prompt 与校验逻辑 | 手写版 | 少一层抽象，异常栈直指代码行 |
| 要加多轮追问、工具调用、RAG | LangChain 版 | `Runnable` 组合与 memory 组件现成 |
| 只跑一次固定查询 | 手写版 | 不值得为一次调用引入框架依赖 |

两版共用 `validate()` / `run_sql()` / `rule_based()`，任何一处修复同时生效，不会漂移。

# 第 4 周 · 可视化设计说明

> 三端可视化：Superset 仪表板（BI）、ECharts 数据大屏（汇报）、Streamlit 问答（自助分析）。
> 本文只写"为什么这么画"，不重复操作步骤。

---

## 一、三端各管什么

| 端 | 使用者 | 核心诉求 | 因此的设计取舍 |
|---|---|---|---|
| Superset 仪表板 | 运营 / 分析师 | 自助探索、钻取、换维度 | 用成熟 BI 的图表库与筛选器，不自己造轮子 |
| ECharts 大屏 | 汇报现场 / 大屏投放 | 一屏看懂、远距离可读 | 固定 1920×1080 舞台，不追求自适应布局 |
| Streamlit 问答 | 不会写 SQL 的同事 | 问一句给一个答案 | 先出表再出图，SQL 可展开核对 |

三端**共用同一份服务层数据**（`data/serving/*.csv` → MySQL / ClickHouse），
口径来自第 3 周的《指标定义文档》，不各自算一遍。

## 二、Superset 仪表板

### 2.1 结构

8 张图，3 行，12 栅格：

| 行 | 图表 | 类型 | 数据集 | 为什么是它 |
|---|---|---|---|---|
| 1 | ① 日 GMV 趋势（月度聚合） | 折线 | ClickHouse `sales_daily` | 时间序列看趋势，折线最直观；`dt` 是真 `Date` 类型，时间轴天然可用 |
| 1 | ② 月度 GMV 分布 | 柱状 | MySQL `monthly` | 12 个月做离散比较，柱状比折线更强调"每月一个值" |
| 1 | ③ 月度 GMV 趋势（联动用） | 折线 | MySQL `monthly` | 与 ② 同数据集同维度，用于演示图表联动 |
| 2 | ④ 品类 GMV 构成 | 环图 | Hive `ads_category_topn` | 8 个品类的占比，环图 + 中心留白比饼图更清爽 |
| 2 | ⑤ 门店 GMV 排行 Top10 | 明细表 | Hive `ads_store_rank` | 排行需要精确数值，表格比条形图更适合核对 |
| 2 | ⑥ 省份 GMV 分布 | 中国地图 | MySQL `region` | 地域分布只有地图能一眼看出"哪里强哪里弱" |
| 3 | ⑦ 用户价值分层 | 环图 | Hive `ads_user_segment` | 5 个价值段，环图看结构 |
| 3 | ⑧ 渠道 GMV 构成 | 环图 | Hive `ads_channel_sales` | 4 个渠道的占比 |

三行的高度分别是 1 行趋势 / 1 行结构 / 1 行占比，7、8 两张环图各占半幅——
**环图放窄卡片时，外置标签会被裁成"母婴玩具: 11…"**，实测 3 栅格宽度（约 190 px）
必裁，6 栅格（约 400 px）才够。

### 2.2 三个必须记住的坑

**（1）地图的关联键写死在 `properties.ISO` 上**

Superset 的 `country_map` 前端代码里是这一行：

```js
const r = n.filter((e) => e.country_id === t.properties.ISO)
```

`t.properties.ISO` 是内置中国底图（`b9778042dc757099d17d.geojson`，34 个要素）里的
行政区码，形如 `CN-SN`。所以 entity 列必须给 **ISO 3166-2 码**，
传中文省名（`陕西省`）或英文省名（`Shaanxi`）都会匹配不到——地图能画出边界，
但一个省都不着色，也不出图例。

这也解释了为什么服务层的 `region` 表要多存一列 `iso`：分析用中文名，落图用 ISO 码。

**（2）`FEATURE_FLAGS` 是整体覆盖，不是合并**

在 `superset_config.py` 里写 `FEATURE_FLAGS = {...}` 会把 `config.py` 里的默认项**全部丢掉**，
包括 `DASHBOARD_CROSS_FILTERS`。表现是仪表板能正常显示，但点柱子没有任何联动反应。
必须显式补 `"DASHBOARD_CROSS_FILTERS": True`。

**（3）图表配置走 ORM，不走 REST**

用 `/api/v1` 建数据源/图表连撞三堵墙：写接口要 CSRF（纯 Bearer → 400）、
补 Cookie 后 GET 列表 422、建 Hive 数据源时探测 `SHOW CATALOGS` 又 422。
最终改成在容器内用 Superset 自己的 ORM 写库（`superset/provision.py`），
绕开整条认证链路，且**幂等可重跑**——图表名就是幂等键，改完参数重跑一次即生效，
废弃的旧图表会被脚本自动清掉。

### 2.3 联动筛选的现状（如实记录）

- **原生筛选器「月份」**：`filter_select`，目标列 `monthly.month`，作用域绑定
  ②③ 两张图，下拉能加载出 12 个选项。
- **图表交叉筛选**：`emitCrossFilters` + `chart_configuration` 作用域 +
  `DASHBOARD_CROSS_FILTERS` 开关三项都已配置，但**实测点击柱子只弹出 tooltip，
  未触发其它图表联动**，用真实鼠标点击（非合成事件）复现同样结果。

结论：**联动筛选按"原生筛选器"交付，交叉筛选作为待办记录**，
不把"配置了"说成"验证通过"。复现证据见 `docs/images/w4_superset_crossfilter.png`
（用真实鼠标点击柱状图 ② 的 2024-01 柱，tooltip 正常弹出、③ 折线未变化）。

## 三、ECharts 数据大屏

### 3.1 七个面板

| 面板 | 图表 | 设计要点 |
|---|---|---|
| 月度成交趋势 | 柱状 + 折线双轴 | 柱子是 GMV，折线是环比；环比有正负，必须用第二条 Y 轴，否则柱子被压平 |
| 下单时段 × 品类热力 | 热力图 | 见 3.2，本屏最费劲的一张 |
| 品类销售构成 | 横向条形 | 8 个品类名较长，横向条形的标签有足够横向空间 |
| 区域分布 | 横向条形 TOP12 | 15 个省份全画会挤，取 TOP12 + "其余"；顺序按 GMV 降序 |
| 门店经营质量 | 散点（气泡） | X=客单价、Y=GMV、气泡大小=订单量，一张图看三个指标，能识别"高价低频"与"低价高频"两类门店 |
| 支付方式占比 | 环形图 | 4 类，环形比饼图省地方 |
| 门店 GMV 排行 | 自定义 HTML 条 | 排行榜用 DOM 画比用图表库更可控（能加名次、能对齐小数点） |

### 3.2 热力图的两次返工

**第一版：绝对金额。** 结果整片颜色几乎一样，看不出任何规律。
排查发现明细表的 `unit_price` 是**标价**不是成交价：`SUM(quantity × unit_price)` 算出来 6.17 亿，
而订单实付是 3,611 万，**差 17 倍**。任何按明细金额做的占比分析都会失真。

**第二版：改成订单数。** 好了一些，但仍然偏均匀——每个时段每个品类都有单，
绝对值差异被"总单量"这个基数抹平了。

**第三版：行内归一化。** 每个格子显示"该品类该时段的订单 ÷ 该品类全天订单"，
即**占该品类全天比重**。这样每个品类自己跟自己比，规律立刻出来：
生鲜在 17–19 点集中，图书文娱在 21–23 点集中。

```javascript
const data = h.data.map(([hh, ci, pct]) => [hh, ci, pct]);
formatter: (p) => `${hours[p.data[0]]}:00　<b>${cats[p.data[1]]}</b><br/>`
  + `订单 ${rawOrders[key]} 单　占该品类全天 ${p.data[2].toFixed(2)}%`
```

tooltip 里同时给出**原始订单数**和**占比**，避免"百分比很唬人但基数只有 3 单"的误读。

### 3.3 自适应方案：固定舞台 + 整体缩放

```javascript
const s = Math.min(window.innerWidth / 1920, window.innerHeight / 1080);
stage.style.transform = `translate(-50%, -50%) scale(${s})`;
```

没有用 rem / vw / 百分比布局，理由是：**大屏的版式是设计出来的，不是流出来的**。
用响应式布局，1366×768 的笔记本和 4K 大屏上会得到两种完全不同的信息密度，
字号、间距、图表比例全都要重新调。固定 1920×1080 舞台再整体缩放，
任何分辨率下看到的**都是同一张图**，只是大小不同——这才是大屏要的效果。

代价：极端宽高比（如 21:9）两侧会留黑边。这个代价可以接受。

### 3.4 数据加载双通道

```javascript
// 优先走后端 API，失败回落页面内联数据
try { data = await (await fetch(API)).json(); }
catch { data = window.DASHBOARD_DATA; }
```

`export_dashboard_data.py` 同时产出三份：`dashboard.json`（给 API）、
`dashboard.js`（把数据挂到 `window.DASHBOARD_DATA`，给 `file://` 直接打开用）、
`data/serving/*.csv`（给 MySQL / ClickHouse 灌数）。
这样**答辩现场断网、没起容器，双击 HTML 也能演示**。

## 四、Streamlit 问答界面

### 4.1 一次提问的完整链路

```
输入问题
  → 拼 Prompt（表结构 + 11 条硬约束）
  → 模型生成 SQL
  → 静态校验（单条 SELECT / 表白名单 / 强制 LIMIT）
  → pyhive 执行
  → 失败则把数据库报错喂回模型改一次（max_retry=1）
  → 结果表 + 图表双 Tab
```

界面上会把这条链路的中间态都摊开：`大模型` / `执行 0.0s` / `返回 12 行` /
**`已自修复 1 次`**，SQL 收在可展开的折叠块里。这样回答错了能立刻定位是
"模型理解错"、"SQL 写错"还是"数据本身如此"。

### 4.2 图表为什么不用 `st.bar_chart`

作业要求把 ECharts 渲染逻辑嵌进问答界面，所以 `echarts_html()` 生成一段完整的
HTML + `st.components.v1.html` 内联渲染，图表库用本地 `vendor/echarts.min.js`，
不依赖 CDN。图表类型由 `guess_kind()` 按结果集形状自动推荐：
1 个维度 + 1 个度量 → 柱/折线，含时间列 → 折线，占比类 → 饼图，
其余 → 表格；用户可在 4 种类型间手动切换。

### 4.3 一次真实的失败与修复

问"2024 年每个月的 GMV 趋势"，模型第一版写的是：

```sql
SELECT month, SUM(gmv) FROM ads_monthly_trend WHERE year = '2024' GROUP BY month
```

`ads_monthly_trend` 只有 `month`（形如 `2024-06`），没有 `year` 列，Hive 报
`SemanticException [Error 10004]: Invalid table alias or column reference 'year'`。

处理分两层：

1. **Prompt 加约束**：第 11 条明确"按年份/月份筛选前先确认这张表有没有对应日期列，
   没有就写 `WHERE month LIKE '2024-%'`，不要凭空造 `year`"；
2. **执行期自修复**：`ask_with_repair()` 把报错原文回灌给模型让它改一次。

这类错误**静态校验拦不住**（语法完全合法，只是列不存在），只能靠执行期兜。

## 五、口径一致性：三端必须同源

| 检查点 | 结果 |
|---|---|
| Hive `ydsh_ads.ads_sales_daily_report` 全年 GMV | 36,116,687.06 |
| ClickHouse `ydsh_ads.sales_daily` 全年 GMV | 36,116,687.06 |
| MySQL `ydsh_ads.sales_daily` 全年 GMV | 36,116,687.06 |
| Superset ① 折线 12 个月合计 | 36,116,687.06 |
| ECharts 大屏月度趋势合计 | 36,116,687.06 |

五处一致，说明"从 Hive 导出 → 灌 MySQL/CK → 三端读取"这条链没有引入偏差。
这也是为什么 `export_dashboard_data.py` 被设计成**唯一取数出口**：
它同时写 JSON / JS / CSV，任何一端的数不一致，一定是有人绕过了它自己查库。

## 六、还差什么

1. **移动端**：三端都只按桌面宽度设计，大屏在手机上不可用（可以接受，本来就不是手机场景）。
2. **暗色主题**：Superset 用的是默认亮色，大屏是暗色，切换时观感割裂。
3. **图表联动**：见 2.3，交叉筛选未验证通过。
4. **下钻**：目前所有图都是"汇总到某一层"，没有做点击下钻到明细（Superset 的 drill-to-detail 需要额外配置列映射）。

## 一、没有大模型 Key

### 1.1 为什么不能凭空解决

API Key 绑定账号与计费，属于外部凭证，任何代码都无法生成。这一点必须说清楚，不能含糊成「已优化」。

### 1.2 已经做到的：把「缺 Key」拆成可验证的结论

配 Key 之前，最怕的是拿到 Key 后还要再调一轮代码。所以这一轮做了三件事：

| 通义千问 | `DASHSCOPE_API_KEY` | qwen-plus | 百炼有免费 token |

全部走 OpenAI 兼容协议。任何一家有 Key 就能跑，要新增第六家只改 `PROVIDERS` 字典，三个脚本自动生效。

**（2）五家连通性实测：证明只差密钥**

用无效 Key 分别请求五家接口（`python python/llm_ping.py --provider <name>`）：

| 服务商 | 耗时 | 返回 |
|---|---|---|
| DeepSeek | 0.6s | `401 Authentication Fails, Your api key: ****0000 is invalid` |

这个结论的价值：**配 Key 之前就能确定，剩下的唯一变量就是密钥本身**，不需要再改代码、调网络或猜格式。

LangChain 版的降级链是 `结构化输出 → 纯文本 → 规则`，见 `docs/NL2SQL设计与测试报告.md` 第 8.3 节。没有 Key 时链路仍然跑完，且输出明确标注模式，不会让规则结果被误当成模型能力。

## 二、未使用 LangChain

### 2.1 已解决

新增 `python/nl2sql_chain.py`，按任务书要求的技术栈实现，与手写版共用同一套校验器、执行器与 Schema，只替换编排层。

| 环节 | 手写版 | LangChain 版 |
|---|---|---|
| Prompt | 手工拼 dict | `ChatPromptTemplate`，few-shot 声明式管理 |
| 输出解析 | 正则抽代码块 | `with_structured_output(SQLPlan)` + Pydantic |
| 降级 | `if/else` 判断有无 Key | `with_fallbacks` 三级自动降级 |
| 编排 | 顺序调用函数 | LCEL 管道 |
| 可观测 | 无 | 链路图 + Callback 计时 |

### 2.2 为什么不是「换个壳」

三个具体收益，都有实测：

- **结构化输出**：模型返回 `{sql, tables_used, reasoning}`，不用正则从自然语言里抠 SQL，还顺带产出可审计的选表理由。
- **降级声明化**：三级降级是一行 `with_fallbacks([text_chain, rule_chain])`。手写要实现同等逻辑得三层嵌套 `try/except`。
- **链路可视化**：`--graph` 直接打印管道结构，不用读代码。

### 2.3 一个刻意的设计

没有 Key 时，主链不是被 `if/else` 绕开，而是**真的抛异常交给 fallback 接住**。

理由是降级机制本身需要被持续验证。如果每次都在外层判断完事，fallback 分支可能早就因为接口变更失效了，等到真出事才发现——那时候降级也救不了场。

### 2.4 A/B 对照

```bash
python python/nl2sql_chain.py --compare
```

```
SQL 完全一致：6/6   |   两版均执行成功：6/6
```

结果写入 `data/nl2sql_ab_compare.json`。

**局限要说明**：两版都跑在规则模式下，SQL 一致是必然的（同源）。这次对照证明的是「编排层替换后行为等价、无回归」，不是「两版在真实模型下的质量差异」。后者需要配 Key 后重跑。

### 2.5 两版都保留的理由

| 场景 | 建议 |
|---|---|
| 作业评审，要求指定技术栈 | LangChain 版 |
| 调试 Prompt 与校验逻辑 | 手写版（异常栈直指代码行） |
| 要加多轮追问 / 工具调用 / RAG | LangChain 版 |
| 只跑一次固定查询 | 手写版（不值得引入框架依赖） |

两版共用 `validate()` / `run_sql()` / `rule_based()`，修复一处同时生效，不会漂移。

## 三、未真实执行 Fork

### 3.1 先确认限制到底来自哪里

原来只说「个人仓库无法 Fork 自己」，是经验判断。这次做了实测：

```bash
curl -X POST https://api.github.com/repos/kitty616/ydsh-week1/forks
# → HTTP 202，返回体是原仓库信息
```

返回 202 看起来像成功。但紧接着查：

```
账号下仓库总数：1（只有 ydsh-week1，无 fork）
原仓库 forks_count：0
network_count：0
```

**说明 GitHub 对「fork 自己的仓库」是静默 no-op**：API 不报错、不创建仓库、forks_count 不变。这不是权限问题，是产品规则——一个仓库不能 fork 它自己，同一 fork network 里也不允许存在第二个 fork。

### 3.2 两条可选的解决路径

**路径 A：真正执行 Fork（约 30 秒人工 + 全自动）**

Fork 需要一个「非当前账号」的上游所有者。GitHub 不提供创建组织的 API，所以这一步必须人工：

1. 打开 https://github.com/organizations/plan ，选 Free 创建一个组织（只需起个名字）
2. 告诉我组织名

剩下的全部可以自动完成：在组织下建上游仓库并推入现有历史 → 个人账号 fork 该上游 → 在 fork 上开分支开发 → 向上游提 PR → Review → 合并 → 打标签。每一步都产生真实的 GitHub 对象，`forked from` 标记也会真实出现。

**路径 B：维持等价流程（当前状态）**

不建组织的话，功能分支 + PR 已经是 Git 协作的全部原语的真实执行：

| Fork 工作流环节 | 当前实现 | 是否真实发生 |
|---|---|---|
| 从上游复制仓库到自己名下 | 功能分支代替 | ❌ 平台限制 |
| 在副本上开发 | `feature/week3-dws-ads`、`docs/week3-git-log` | ✅ |
| 向上游提 PR | PR #2、#3 | ✅ |
| Code Review | 5 条行内评论 + 等级判定 | ✅ |
| 冲突解决 | README 速查表逐列取并集 | ✅ |
| Issue 追踪 | Issue #1，验收标准先行 | ✅ |
| 合并与标签 | Merge commit + `week3-done` | ✅ |

七项里六项真实发生，缺的只有「复制仓库到自己名下」这一步——而这一步本身没有技术含量，只是点一下按钮。

**建议**：如果评审只要求「掌握 Fork 工作流」，路径 B 的证据链已经完整（`docs/Git协同记录.md` 第六节逐条对比）。如果明确要求在 GitHub 上看到 `forked from` 标记，走路径 A，30 秒的事。

### 3.3 这次实测的附带收获

`POST /forks` 返回 202 却什么都没创建，这个行为很容易被误读为「fork 成功了」。

如果只看到 202 就写进文档说「已完成 Fork」，答辩时被要求打开 fork 仓库就会当场露馅。**接口返回成功码不等于业务成功**，得去查状态字段验证——这和第 3 周 Code Review 里发现的「测试断言只看布尔值」是同一类错误：验证的对象选错了。

### 3.4 补记：路径 A 也有前置条件

准备走路径 A 时发现访问不到建组织页面（浏览器 `ERR_CONNECTION_RESET`），于是补测了一次域名粒度的连通性：

```bash
for u in https://github.com https://api.github.com; do
  curl -sS -o /dev/null -m 8 -w "$u  %{http_code}  %{time_total}s\n" "$u"
done
# https://github.com        000  8.0s     ← 超时，网页打不开
# https://api.github.com    200  0.55s    ← 正常
```

同一个站点的网页不通、API 通。这与本周期早先 `git push` 报 `schannel: unexpected eof`、改用 Git Data API 才推上去的现象是同一条网络路径问题：**`github.com` 的 HTML 与 git 协议被干扰，`api.github.com` 可用**。

对路径 A 的影响：GitHub 没有「创建组织」的公开 API（`POST /admin/organizations` 仅 GitHub Enterprise Server 有），建组织只能在网页上点。所以路径 A 多了一个前置条件——**先在能打开 github.com 的环境里完成那 30 秒**。路径 B 不受影响，因为它的全部操作都已经走 `api.github.com` 完成。

#### 11-10 补测：这一段网络已恢复

上面那次测量只代表当时的状态，不能当成永久结论。同一台机器同一天稍晚复测，两个域名都通了：

```bash
# 11-10 07:4x 复测
# https://github.com        200  1.10s     ← 已恢复
# https://api.github.com    200  0.52s
```

直接 `git push` 也一次成功（`232ee1b..544884c`），不再需要 `--force-with-lease` 之外的任何绕行，也不再需要 Git Data API 代推。

**这里更正的是我自己的一段判断。** 原文写「github.com 网页不可达」，读起来像一条稳定事实，实际只是十几分钟窗口内的现象。网络故障是时间相关的状态，不是属性——它会在一次会话里变好，也会在另一次里变坏。把它写成不带时间戳的结论，等于给后来的人留了一个会过期的前提。

所以路径 A 现在的前置条件只剩一个：**建组织这 30 秒得由账号持有人操作**（没有公开 API 可用）。网络不再是障碍。

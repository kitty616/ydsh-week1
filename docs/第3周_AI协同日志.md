## 四、问题与解决

**问题 1：AI 写的 SQL 能跑，但结果是错的**

最典型的是相对时间（第 3 条）。`current_date()` 写法完全合法，Hive 也不报错，只是返回空结果。空结果看起来像"这段时间没销售"，很容易被当成业务结论写进报告。解决办法不是改提示词措辞，而是**从源头消除不确定性**：把数据真实日期区间注入提示词，并明令禁止 `current_date()`。

**问题 2：AI 的参数建议与实测相反**

第 4 条里，"`level=low` 能降低思考量"听上去完全合理，实测却是思考翻倍、正文归零。这件事的教训不是"AI 不可信"，而是**凡是涉及具体版本的参数，必须以实测为准**——模型对自家 API 细节的描述同样会过时。

**问题 3：AI 判错根因，但错得很有说服力**

第 5 条关于 Fork 失败，AI 给出的"权限不足"是一个标准答案，还配了操作步骤。如果按它说的去重新授权，会白折腾一轮且问题依旧。破局点是**不信 HTTP 状态码，去查业务字段**：202 是"已受理"不是"已完成"。

## 五、反思与总结

**AI 协同带来的价值**

主要在"起步速度"和"挑毛病"两件事上。写建表语句、搭特征工程、列校验用例这类有固定套路的工作，AI 能把时间从几小时压到几分钟；第 7 条的文档 Review 也能挑出人容易忽略的悬空引用。

**AI 的局限与风险（本项目的实际观察）**

1. **它会给出自信的错误答案，且错在"看起来最对"的地方。** 第 3、4、5 条都是这样：方案逻辑自洽、格式规范、还配了操作步骤，唯独结论是错的。
2. **它不会质疑数据本身。** 复购率 100%、四个渠道各占 25% 这种明显失真的数据，AI 只会顺着往下分析，不会说"这份数据有问题"。批判性必须由人提供。
3. **它对自家产品的细节会过时。** 参数名、行为、限制，都要以实测为准。
4. **依赖风险是真实的。** 一旦模型不可用，规则链必须能兜住——这也是为什么 `nl2sql.py` 保留了 `rule_based()` 兜底，并让 `--batch` 在无 Key 时仍可跑通。

**本次协作中我的能力提升**

最大的变化是**从"让 AI 给答案"转成"让 AI 给候选、我来验证"**。具体做法有三条：一是任何数字都要有出处（脚本产出或 Hive 查询），不接受模型口述；二是涉及平台规则/API 参数，一律实测；三是文档里的每个结论都要能在代码里找到对应实现——这也是第 8 条那个阈值不一致能被发现的原因。

**对 AI 协同的改进建议**

- 提问时把"约束"讲全（表名白名单、日期范围、别名规范），比事后改错省时间
- 让 AI 一次只做一件事。第 6 条的教训很直接：给三个任务，它会把 token 全花在思考上，一个都交不出来
- 把 AI 当"能干的实习生"而不是"权威"：它的产出必须过我的校验流程，这个流程本身要写下来、能复现

## 一、总体架构

系统由"**一条数据主线 + 三个消费端 + 一套编排**"组成：

```
                 ┌──────────────────────────── 数据主线 ────────────────────────────┐
   6 个 CSV ──► ODS ──► DWD ──► DWS ──► ADS ──┬──► MySQL 服务层（6 表）
   114,809 行    原始    明细    汇总    应用   ├──► ClickHouse 加速层（4 表）
                  │       │       │       │    └──► 大屏快照 JSON/CSV
                  │       │       │       │
                  │       │       │       └────► Superset 仪表板（8 图）
                  │       │       └────────────► Streamlit 问答（NL2SQL）
                  │       └────────────────────► 预测模型（7 天 GMV）
                  └────────────────────────────► 探索性分析、数据质量报告

                 └──────────── Docker Compose 7 服务统一编排 ───────────────────────┘
```

| 层 | 技术 | 职责 | 规模 |
|---|---|---|---|
| 存储 / 计算 | Apache Hive 4.0 + Tez | 四层数仓，ORC + SNAPPY，`dwd_order` 按日分区 | 27 张表 / 366 分区 |
| 元数据 | MySQL 8（Hive Metastore） | 表结构、分区、权限 | — |
| 服务层 | MySQL 8 `ydsh_ads` | 低延迟查询，供 BI 与前端 | 6 张宽表 |
| 加速层 | ClickHouse 24 | 高并发聚合，压测 QPS 924.83 | 4 张 MergeTree |
| BI | Superset 4.1.1 | 仪表板、筛选器、地图 | 3 数据源 / 10 数据集 / 8 图 |
| 大屏 | ECharts 5.5.1 | 7 面板 5 类图表，离线可用 | 单页 1920×1080 |
| 问答 | Streamlit 1.40 | NL2SQL 闭环 + 图表渲染 | 1 应用 |
| 取数 API | Python 标准库 HTTP | 大屏 JSON 接口，CORS 开放 | 3 端点 |
| 编排 | Docker Compose | 一键起 7 服务，healthcheck 串联 | 7 容器 |

## 二、四层数仓设计

### 2.1 ODS：原始层（6 张表 / 114,809 行）

**原则：原样落地，不做任何清洗。** 这一层的价值是"可回溯"——任何清洗争议都能回到
原始行对质。因此保留脏数据（1,902 条日期格式不规范的行仍在），仅统一为 STRING 类型。

### 2.2 DWD：明细层（20 张表）

| 类型 | 表 | 说明 |
|---|---|---|
| 事实 | `dwd_order` | 14,398 行，按 `order_date` 分 366 个分区 |
| 事实 | `dwd_order_item_clean` | 34,580 行，剔除 718 条 `quantity ≤ 0` 及孤儿明细 |
| 维度 | `dim_product` / `dim_store` / `dim_user` / `dim_date` / `dim_channel` / `dim_pay_type` / `dim_order_status` / `dim_member_level` / `dim_behavior_type` | 9 张维表，含退化维度与枚举字典 |
| 过程 | `dwd_*_clean`、`dwd_order_bucket` | 清洗中间结果，便于复算与排查 |
| 质量 | `dq_report` / `dq_compare` | 逐规则体检 + 修复前后对比 |

**建模选择**：采用**维度建模（星型）**而非范式化。理由是新零售分析以"按维度切片看指标"
为主，星型模型 join 少、可读性强，且 Hive 列存下宽表扫描成本可控。

**分区策略**：只有 `dwd_order` 分区（366 个），因为它是唯一会被"按日期范围"反复扫描的
大表。维表只有几十到一千行，分区反而增加元数据开销。**分区不是越多越好，是按访问模式定。**

### 2.3 DWS：汇总层（7 张表）

| 表 | 粒度 | 行数 |
|---|---|---|
| `dws_trade_day` | 日 × 全站 | 366 |
| `dws_trade_week` | 周 × 全站 | 53 |
| `dws_trade_month` | 月 × 全站 | 12 |
| `dws_category_day` | 日 × 品类 | 3,043 |
| `dws_store_day` | 日 × 门店 | 10,566 |
| `dws_channel_day` | 日 × 渠道 | 1,464 |
| `dws_user_stat` | 用户 | 1,000 |

**关键设计：留存时间粒度。** 第 2 周的汇总表是"全期一条"，只能看总览；
第 3 周改成保留日/周/月粒度，才能支撑趋势、环比、预测。
**汇总层一旦丢了时间维度，就再也算不出趋势了。**

**金额分摊规则（品类维度特有）**：明细表 `unit_price` 是**标价**而非成交价，
直接汇总会得到 6.17 亿（实付的 17 倍）。因此品类 GMV 采用
「按 `quantity × unit_price × (1-discount)` 的权重，把订单实付金额分摊到各品类」，
保证品类求和 = 订单实付总额。

**可加性原则**：汇总表**不在存储层做四舍五入**。分组取整再相加会累积舍入漂移
（实测 3,043 个分组累积 0.13 元），取整交给展示层。

### 2.4 ADS：应用层（10 张表）

| 表 | 服务对象 | 行数 |
|---|---|---|
| `ads_kpi_core` | KPI 卡片 / 问答 | 10 个指标 |
| `ads_kpi_overview` | 总览 | 8 |
| `ads_sales_daily_report` | 日销报表 / 大屏 | 366 |
| `ads_monthly_trend` | 月度趋势 | 12 |
| `ads_category_topn` | 品类 TopN | 8 |
| `ads_store_rank` | 门店排行 | 15 |
| `ads_region_sales` | 区域地图 | 15 |
| `ads_channel_sales` | 渠道构成 | 4 |
| `ads_user_segment` | 用户分层 | 5 |
| `ads_user_value` | 用户价值明细 | 1,000 |

ADS 层的定位是"**为消费端准备好形状**"：字段名即展示名，比率类指标预先算好，
行数控制在千级以内，让 BI 拖拽与前端取数都不用再做二次加工。

## 三、应用层架构

### 3.1 三条消费链路

| 消费端 | 链路 | 特点 |
|---|---|---|
| Superset | Superset → Hive / MySQL / ClickHouse（三种数据源并存） | 面向分析人员，可自助拖拽 |
| 数据大屏 | 浏览器 → `/api/dashboard.json` → 失败回落内联快照 | 面向演示，断网也能跑 |
| 智能问答 | Streamlit → `nl2sql` → `hive_client` → HiveServer2 | 面向业务，自然语言问数 |

**为什么 Superset 要接三个数据源而不是一个**：这不是炫技，是为了实测"同一份汇总数据
放在不同引擎上，BI 体验差多少"。实测结果是 ClickHouse 响应最快、Hive 最慢但数据最全，
MySQL 居中——这个对比直接支撑了第 4 周的引擎选型结论。

### 3.2 双通道取数（大屏的关键设计）

大屏优先调 API 拿实时数据，接口不通时回落到构建时写入的 `window.DASHBOARD_DATA` 快照。

- **优点**：演示现场网络/容器出问题时，大屏仍然能完整展示；
- **代价**：快照会过期。因此页面上标注了数据时间戳，不假装是实时的。

### 3.3 NL2SQL 的边界设计

| 防线 | 机制 | 拦住什么 |
|---|---|---|
| 提示词 | 只允许单条 SELECT，禁止 DDL/DML | 模型"顺手"建表删表 |
| 静态校验 | 表名白名单 + 危险关键字正则 + 强制 LIMIT | 越权访问、全表扫描 |
| 执行期 | 报错回灌模型自修复一次（`max_retry=1`） | 列名写错、函数用错 |
| 兜底 | 大模型不可用时走规则匹配 | API 欠费/超时导致整站不可用 |

**设计立场**：AI 只负责"翻译"，不负责"决策"。所有结果都必须能落到一条可读的 SQL 上，
让人能复核。不把模型的自然语言结论直接当答案。

## 四、部署架构

```
                      ┌──────────── 宿主机（Docker Engine）────────────┐
  localhost:8088 ───► │ superset ──┐                                  │
  localhost:8501 ───► │ app ───────┼──► hive-server:10000 ──► metastore │
  localhost:8000 ───► │ api        │         │                    │     │
  localhost:8123 ───► │ clickhouse │         └──► HDFS 本地存储     │     │
                      │            │                              ▼     │
                      │            └──────────────────────────► mysql   │
                      └───────────────────────────────────────────────┘
```

| 服务 | 端口 | 依赖 | 健康检查 |
|---|---|---|---|
| mysql | 3306 | — | `mysqladmin ping` |
| hive-metastore | 9083 | mysql | TCP 9083 |
| hive-server | 10000 | metastore | TCP 10000 |
| clickhouse | 8123 / 9000 | — | `SELECT 1` |
| superset | 8088 | mysql | `/health` |
| app | 8501 | hive-server, clickhouse | TCP 8501 |
| api | 8000 | app | TCP 8000 |

**启动顺序靠 `depends_on: condition: service_healthy` 保证**，而不是靠 `sleep` 猜时间。
`superset` 容器覆盖了官方 CMD，先跑 `bootstrap.sh`（等 MySQL → 建库 → `db upgrade` →
`create-admin` → `init`）再起 Web 服务；不覆盖 CMD 会跳过建库，表现为 worker 反复退出。

**密钥管理**：所有口令走 `.env` + `${VAR:?}` 语法，变量缺失时 `docker compose up`
直接报错退出。**不给默认值**——默认值一旦写进仓库，等于把生产口令公开。

## 五、技术选型与取舍

| 决策点 | 选择 | 备选 | 理由 |
|---|---|---|---|
| 数仓引擎 | Hive 4.0 + Tez | Spark SQL / Doris | 课程要求四层数仓；Hive 生态完整，Metastore 可与 Superset 直连 |
| 表格式 | ORC + SNAPPY | Parquet / TextFile | ORC 谓词下推与压缩率更好，Hive 原生优化充分 |
| 服务层 | MySQL | PostgreSQL | 与 Metastore 复用同一实例，降低编排复杂度 |
| 加速层 | ClickHouse | Doris / Druid | 单机部署轻、聚合极快，压测 QPS 是 Hive 的 200 倍量级 |
| BI | Superset 4.1 | Metabase / Grafana | 开源、支持多数据源、有中国地图 |
| 大屏 | ECharts 5.5 | DataV / AntV | 免费、可离线、图表类型全 |
| 问答前端 | Streamlit | Gradio / 自研 | 开发成本最低，`AppTest` 可做无头测试 |
| 容器编排 | Docker Compose | K8s | 单机演示场景，K8s 过重 |
| Hive 访问 | pyhive | beeline / JDBC | 程序内直连比启动 beeline 客户端快一个数量级（0.3~0.8s vs 数秒） |
| Superset 配资产 | 容器内 ORM 脚本 | REST API | REST 有三堵墙（CSRF / Bearer+Cookie 冲突 / `SHOW CATALOGS` 探测），ORM 幂等且稳定 |

### 关键取舍说明

1. **为什么不用 Spark**：数据量 1.4 万行，Spark 的启动开销（秒级）比计算本身还大。
   Hive on Tez 在这个量级已经绰绰有余，且与 Metastore 集成更自然。
2. **为什么保留 Hive 而不是全量迁 ClickHouse**：Hive 承担"重、全、可追溯"的离线加工，
   ClickHouse 承担"快、并发"的在线查询，两者职责不同。**全量迁移会丢掉分层与可回溯性。**
3. **为什么 Superset 用 ORM 而不是 REST**：REST 建 Hive 数据源时会探测 `SHOW CATALOGS`，
   `apache/hive:4.0.0` 不认这个命令，直接 422。改容器内 ORM 既绕开认证层，又能幂等重跑。

## 六、已知问题与架构层面反思

| 问题 | 架构层原因 | 现状 |
|---|---|---|
| 小数据量下 Hive 性能优势体现不出来 | 事实表仅 1.4 万行，Tez 每次约 0.5 秒的容器启动开销盖住扫描差异 | 已在压测报告中说明，判据改用执行计划而非秒表 |
| 明细金额与订单金额差 17 倍 | 源数据 `unit_price` 是标价，缺"成交价"字段 | 用权重分摊规避；根治需源系统补字段 |
| 0.97% 订单无法归品类 | 明细被整单清洗后，汇总层用 inner join 吞掉了空集 | 已改为「未知品类」显式单列 |
| Superset 交叉筛选不生效 | 4.1 版本前端行为，配置项齐全但点击不联动 | 用原生筛选器替代，如实记录 |
| 单机部署，无高可用 | Compose 单节点，无副本 | 课程演示场景可接受；生产需 K8s + 多副本 |

**一条架构层面的反思**：这套架构最大的价值不是"用了多少组件"，而是
**每一层都有明确的责任边界和可对账的出口**。联调时之所以能在 30 秒内定位到
"品类维度少了 0.97%"，是因为每个维度都能独立求和、独立比对——
**如果当初把所有指标揉进一张大宽表，这个 bug 永远找不出来。**

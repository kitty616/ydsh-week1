## 第一部分 · 五周是怎么一步步实现的

### 1.1 总览：每周解决一个问题，每周留下一个能被验证的东西

| 周 | 主题 | 核心动作 | 关键产出 | 可当场验证的数字 |
|---|---|---|---|---|
| W1 | 环境与原始层 | 起 3 套存储（Hive / MySQL / ClickHouse）、6 个 CSV 原样入库 | `sql/ods/*.sql`、`scripts/import_ods.sh` | ODS **114,809 行**，一列不改 |
| W2 | 数据质量 | 22 条规则、五类脏数据、清洗前后逐项比对 | `sql/clean/*.sql`（8 个）、清洗报告 | 70,979 条问题修 **99.73%** |
| W3 | 数仓建模 + 算法 | 四层建模（27 张表）、时间序列预测、NL2SQL | `sql/dwd` `sql/dws` `sql/ads`、`python/ts_forecast.py`、`python/nl2sql.py` | MAPE **11.79%** vs 基线 13.93% |
| W4 | 可视化 + 部署 | Superset / 大屏 / 问答三端；7 服务 Compose；压测 | `superset/provision.py`、`dashboard/echarts/`、`app/` | CK **924.83 QPS**（Hive 4.17） |
| W5 | 联调 + 收口 | 67 条断言串全链路、五份文档、Git 审查、答辩 | `python/verify_e2e.py`、`docs/项目文档/*` | **64 PASS / 0 FAIL**，约 30 秒 |

**这条主线一句话**：每一周都在给上一周加一道"能被别人独立验证"的关口，到第 5 周变成 67 条自动断言。

### 1.2 每一周具体做了什么

**W1 · 把原始数据搬进来，一行都不改**
6 个 CSV 按原样建 6 张 ODS 表（全 STRING 类型，保留原始形态），`import_ods.sh` 做四步：检查 CSV → 建库建表 → `LOAD DATA` → 行数校验。**ODS 层故意不洗数据**——如果原始层就洗干净了，后面就说不清"到底改了什么"。

**W2 · 先量化脏在哪，再决定怎么修**
22 条规则先跑"评估"（`10_quality_assessment.sql`），把问题**数出来**：缺失值、重复、枚举不统一、异常格式、拆分合并映射，共 70,979 条。然后逐类修（`11`–`23`），每修一类都跑一遍前后比对。关键决策：**不是所有脏数据都该修**——负价明细要剔，但订单本身有效必须留，于是有了"订单完整率 99.03%"这个指标。

**W3 · 四层建模，加两个算法能力**
DWD 20 张表（订单事实按日分区 366 个 + 9 张维表）→ DWS 7 张汇总（日/周/月/品类/门店/渠道/用户）→ ADS 10 张应用表。算法两条腿：`ts_decompose.py` 做趋势-季节分解后 `ts_forecast.py` 出 7 天预测；`nl2sql_chain.py` 做"生成 → 静态校验 → 执行 → 失败回灌自修复"。

**W4 · 三端交付 + 一键起**
Superset 接 3 个数据源、10 个数据集、8 张图；ECharts 大屏 7 个面板（固定 1920×1080 舞台 + 整体 scale，任何分辨率同一张图）；Streamlit 把 NL2SQL 包成界面。7 个服务用 `depends_on` + healthcheck 控顺序，口令全走 `.env`。

**W5 · 串起来跑，抓出藏了两周的问题**
写 67 条断言覆盖 9 个环节，逼着每一层对账。结果抓出 3 个真缺陷，最严重的是品类维度静默丢了 349,609.57 元（0.97%）。修复后 7 个位置 GMV 完全一致。

## 第二部分 · 一条 GMV 的旅程（演示主线，7 个位置同一个数）

这是整场演示的骨架：**跟着一个数走完整条链路**，每停一站报一次数，7 站全是 36,116,687.06。

### 站 0 · 原始 CSV（证明数据不是我造的）

```bash
wc -l data/ods_*.csv
```

预期（含表头）：`15601 / 37550 / 1001 / 601 / 61 / 60001`，合计 **114,815 行**，减 6 个表头 = **114,809 行数据**。

> 台词：这是原始文件，6 个 CSV、11.4 万行，一行没动过。

### 站 1 · ODS 原始层（原样入库）

```bash
docker exec ydsh-hive-server beeline -u jdbc:hive2://localhost:10000 --silent=true \
  -e "SELECT COUNT(*) FROM ydsh_ods.ods_order;"
```

预期：**15,600**

> 台词：ODS 层不做任何清洗，15,600 单原样进来。注意这里是 15,600，下一步会变成 14,398。

### 站 2 · DWD 明细层（清洗 + 去重，GMV 在这里第一次成形）

```bash
docker exec ydsh-hive-server beeline -u jdbc:hive2://localhost:10000 --silent=true \
  -e "SELECT COUNT(*) AS orders, ROUND(SUM(pay_amount),2) AS gmv FROM ydsh_dwd.dwd_order;"
```

预期：**14,398　36,116,687.06**

> 台词：去重和清洗后剩 14,398 单，GMV 36,116,687.06。记住这个数。

### 站 3 · DWS 汇总层（六个维度求和，必须都等于它）

```bash
# 日汇总
docker exec ydsh-hive-server beeline -u jdbc:hive2://localhost:10000 --silent=true \
  -e "SELECT ROUND(SUM(gmv),2) FROM ydsh_dws.dws_trade_day;"

# 品类汇总（这里曾经少 0.97%，现场重点）
docker exec ydsh-hive-server beeline -u jdbc:hive2://localhost:10000 --silent=true \
  -e "SELECT COUNT(*) AS rows_cnt, ROUND(SUM(gmv),2) AS gmv FROM ydsh_dws.dws_category_day;"
```

预期：日汇总 **36,116,687.06**；品类 **3,043 行 / 36,116,687.06**

> 台词：品类这张表是 3,043 行，不是 2,927 行——多出来的 116 行是"日期 × 未知品类"，就是被救回来的那部分。

### 站 4 · ADS 应用层（指标唯一出口）

```bash
docker exec ydsh-hive-server beeline -u jdbc:hive2://localhost:10000 --silent=true \
  -e "SELECT metric_code, metric_name, ROUND(metric_value,2) AS val, unit FROM ydsh_ads.ads_kpi_core;"
```

预期：核心 KPI 长表，其中 GMV 相关行 = **36,116,687.06**

> 台词：ADS 是长表，一个指标一行，带口径说明——这是全项目唯一允许定义指标的地方。

### 站 5 · MySQL 服务层（BI 读的就是它）

```bash
docker exec ydsh-mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -N -e "SELECT ROUND(SUM(gmv),2) FROM ydsh_ads.monthly;" 2>/dev/null'
```

预期：**36116687.06**

### 站 6 · ClickHouse 加速层（同一个数，快 170 倍）

```bash
docker exec ydsh-clickhouse sh -c 'clickhouse-client --password "$CLICKHOUSE_PASSWORD" -q "SELECT round(sum(gmv),2) FROM ydsh_ads.sales_daily"' 2>/dev/null
```

预期：**36116687.06**

### 站 7 · 取数 API（前端读的就是它）

```bash
curl -s http://localhost:8000/api/kpi
curl -s http://localhost:8000/api/health
```

预期：JSON 含 `36116687.06`；health 返回 `{"ok": true, ...}`

> 收尾台词：从 CSV 到浏览器，7 个位置，同一个数。这就是"能自证"的意思。

## 附 · 数字口径对照（万一老师拿两份文档对比）

| 场景 | 品类合计 | 139 笔金额 | 差额 | 出处 |
|---|---|---|---|---|
| 第 2/3 周当时记录 | 35,767,077.63 | 349,609.43 | 349,609.43 | 清洗报告、数仓架构设计（历史快照） |
| 第 5 周联调实测 | 35,767,077.49 | 349,609.44 | 349,609.57 | 联调报告、答辩稿（**以此为准**） |

差异来自品类汇总从"分组 ROUND"改成"存储层不取整"，同一个口径重算会得到不同的尾数。

**被问到就答**：以第 5 周联调实测为准，缺口 349,609.57 = 349,609.44（139 笔实付）+ 0.13（分组舍入漂移）。前两周文档里的 349,609.43 是当时带 ROUND 的版本算出来的，两个缺陷（整单丢失 + 舍入漂移）在修复后才被拆开。

```
修复前：36,116,687.06 − 349,609.57 = 35,767,077.49
拆解：  349,609.57 = 349,609.44 + 0.13
验算：  35,767,077.49 + 349,609.44 + 0.13 = 36,116,687.06 ✓
```

## 三、高频提问与参考回答

### Q1：为什么大额异常用 IQR 而不是 P99？

**答**：因为这批数据的 P99 本身就被污染了——P99 = 563 万，而 P95 只有 4,836 元。分位数是个排序统计量，极端值虽然不改变它的位置，但当 2% 的记录都是百万级时，P99 必然落在百万区间里。用它当“正常上限”，等于拿病人的体温计判断有没有发烧。

改用的判据是箱线图的极端离群线 **Q3 + 3×IQR**：

```
Q1 = 1,293.39    Q3 = 3,809.12    IQR = 2,515.73
上界 = 3,809.12 + 3 × 2,515.73 = 11,356.33 元
```

它的理论假设只有一条：数据的中间 50% 是干净的。这个假设在这批数据里成立。

**这个结论对参数不敏感，我专门验过**：正常订单的最大金额是 **4,999.85 元**，异常值最小也在**百万级**，两者之间有整整三个数量级的空白。所以把系数换成 1.5 倍（上界 7,582.72）、换成 3 倍（11,356.33）、甚至把基准从 Q3 换成 Q1（8,840.59），**三种阈值命中的都是同一批 312 条**，删除行数和最终 GMV 完全一致。

换句话说，这不是调参调出来的结果——只要判据落在 5,000 到 100 万之间的任何位置，答案都一样。之所以仍然报 3 倍，是因为它是箱线图公认的极端离群标准，写进文档别人不用额外解释为什么选这个系数。

### Q2：类目销售额为什么不用「数量 × 单价」直接汇总，而要分摊？

**答**：因为两个口径对不上，而且差了一个量级。明细表里的 `unit_price` 是**吊牌价（原价）**，而订单表的 `pay_amount` 是**实付金额**。直接汇总明细得到 5.34 亿元，订单侧 GMV 只有 3.61 亿元。

分摊做法是：对每个订单，先算各明细的金额占比，再把订单实付金额按占比分给类目。这样两个性质同时成立——单个订单内各类目分到的钱加起来等于实付金额，全局各类目 GMV 之和等于订单总 GMV。

**实测结果**：分摊后 8 个类目合计 35,767,077.63 元，与订单侧 36,116,687.06 元相差 34.96 万元，差额正好对应 139 笔没有明细记录的订单（覆盖率 99.03%）。差额可解释，不是误差。

**如果被追问“为什么不干脆放大折扣率还原”**：试过。用 `discount` 字段还原后总额仍偏高，因为 `discount` 是订单级折扣，明细级只有一个 `discount` 列，而订单里还有优惠券、满减等未落在明细上的金额。分摊是唯一能保证对账的做法。

### Q3：清洗后订单从 15,600 掉到 14,398，删了 1,202 单，会不会把指标做小了？

**答**：1,202 单拆得开——**600 单是重复记录**（`order_id` 完全相同，按业务时间倒序取最新一条保留）、**310 单是负金额**、**312 单是百万级超上限**。后两类共 622 单中有 20 单本身就属于重复记录，去重时已经删掉，所以净减 600 + 602 = **1,202 单**。

**删掉的影响是可以精确量化的，不是“差不多”**：

| 被删记录 | 笔数 | 金额合计 | 若保留的后果 |
|---|---:|---:|---|
| 负金额 | 310 | −810,910.64 元 | 拉低 GMV 约 2.2%，且客单价被低估 |
| 百万级超上限 | 312 | **1,657,808,087.34 元** | GMV 从 3.61 亿虚增到 **19.7 亿**，放大 5.5 倍 |
| 重复记录 | 600 | 重复计数 | 订单量虚高 4%，人均下单次数被高估 |

所以真正致命的不是那 81 万负金额，而是 16.58 亿的异常大额——它单独一项就能把 GMV 抬到真实值的五倍以上。这也解释了为什么不能只看总额：310 笔负值和 312 笔巨额方向相反、会互相抵消一部分，总额“看起来还行”，但结构已经完全错了。

### Q4：枚举字段为什么用「白名单映射 + 兜底值」，而不是简单的 `CASE WHEN ... ELSE`？

**答**：区别在**意外值会不会静默穿透**。`CASE WHEN` 加 `ELSE '其他'`，遇到没预料到的新脏值会悄悄归到“其他”里，你永远不知道进了什么。

白名单写法是：先列出所有合法值，不在白名单里的统一打上 `'未匹配'` 标记，同时保留原始值到一个 flag 字段。这样每次清洗完可以 `SELECT COUNT(*) WHERE enum_flag = '未匹配'`——**当前实测是 0**，说明脏值全部收敛；将来上游新增脏值，这个数会立刻变成非 0，当作监控指标用。

代价是多一列存储，换来的是清洗过程可观测。

### Q5：为什么要分区又分桶？只做分区不够吗？

**答**：两个解决的不是同一个问题。

**分区**解决**裁剪**：`dwd_order` 按 `order_date` 分 366 个日分区，查“11 月的数据”只需扫 30 个目录，而不是全表。这是减少 IO。

**分桶**解决**连接**：`dwd_order_bucket` 按 `user_id` 哈希分 8 桶。当它和同样按 `user_id` 分 8 桶的 `dim_user` 做 join 时，Hive 可以走 Map 端连接——每个 Map 任务只处理第 i 桶的事实和第 i 桶的维度，不需要全表 shuffle。

**实测验证**：`COUNT(DISTINCT INPUT__FILE__NAME) = 8`，确认真的落了 8 个桶文件，不是只写了桶定义。

**如果被追问“小表不是广播更简单”**：是。`dim_user` 只有 1,000 行，广播足够。分桶表是我为了演示 Map 端连接机制额外建的，生产环境里只有当维表大到无法广播（比如几千万行）时，分桶连接才有意义。这一点我写在架构文档的“设计取舍”里了。

### Q6：缺失值为什么只修到 193 项，剩下的是没修完吗？

**答**：是**有意保留**的。193 项全部是 `email` 字段的空值。

判断依据是依赖强度：邮箱不参与任何核心指标计算（GMV、客单价、复购、分层都不用），只在营销触达时才需要。对这种弱依赖字段，**编造一个邮箱比留空危害更大**——它会污染下游的用户画像，而且无法追溯。

处理方式是：保留空值 + 增加 `email_flag = '缺失'` 标记位。下游要用邮箱时按 flag 过滤，明确知道哪部分是缺的。

如果是手机号这种强依赖字段（用于登录、召回），处理方式就不同了——本周手机号非 11 位的记录是置空并打标，而不是编造。

### Q7：你说“数据过于规整、结论需业务核实”，是你的方法有问题还是数据有问题？

**答**：数据的问题，但**发现它恰恰说明方法是对的**。

三条异常规整的现象：四个渠道 GMV 各占约 25%；八个类目各占 11%–15%，极差很小；60 家门店 GMV 极差仅 39%。

真实零售业务里，渠道结构通常严重倾斜（比如 APP 占 60% 以上），类目之间能差十倍，门店之间差三到五倍很正常。三项同时“均匀分布”，概率上不可能自然发生，判断是模拟数据按均匀分布生成导致的。

**我的处理**：SQL 逻辑全部保留并验证过，报告里明确写“方法可用、结论需业务核实”，没有把这些当洞察讲。这比硬讲一个漂亮结论要诚实——如果答辩时把“四渠道均衡”当成业务发现，被问一句“真实业务会这样吗”就崩了。

### Q8：DWS 和 ADS 有什么区别？不都是汇总吗？

**答**：粒度和使用者的区别。

**DWS** 是**面向主题的轻度汇总**，粒度较细，保留多维可切分性。比如 `dws_daily_sales` 是「日 × 门店」粒度，366 天 × 60 店；`dws_category_sales` 是「类目」粒度。它是给分析师用的中间层，你可以拿它再切任意维度。

**ADS** 是**面向应用的最终结果**，粒度就是一个报表要展示的样子。比如 `ads_kpi_overview` 是 8 行 KPI，`ads_store_rank` 是带名次的榜单。它是给看板直接读的，基本不再做二次加工。

一句话：**DWS 可以再算，ADS 拿来就展示**。这样分层的好处是加一个新报表时，多数情况只需在 DWS 上再写一个 ADS，不用回 DWD 重算。

### Q9（可能追问）：为什么 ODS 层所有字段都用 STRING？

**答**：因为**类型转换会掩盖脏数据**。

原始数据里有 `age = 200`、`age = -3`、`pay_amount = -5800`、日期写成三种格式。如果在建表时就声明成 `INT`/`DECIMAL`/`DATE`，Hive 的加载行为是：能转的转，转不了的置 NULL。结果就是——异常值被静默吃掉，你还以为数据干净。

全 STRING 建表，脏值原样保留，到 DWD 层用显式 `CAST` + 条件判断处理，每一步改了什么都有记录。这正是本周能把 70,979 项脏值精确统计出来的前提。

代价是 DWD 层写起来啰嗦，但换来的是**清洗过程完全可审计**。

## 一、为什么要专门做一次联调

前四周每一环都单独验收过：第 2 周清洗、第 3 周数仓与建模、第 4 周可视化与部署。
但"每一环都对"不等于"整条链路对"——**层与层之间的口径、容器与容器之间的配置、
脚本与真实返回值之间的假设，都只在串起来跑的时候才会暴露**。

这次联调写了 67 条断言，覆盖 9 个环节。结果：**64 项通过、3 项告警、0 项失败**，
但过程中抓到了 **3 个真实缺陷**，其中一个让 34.96 万元 GMV 从品类维度里凭空消失。

## 二、抓到的三个真问题

### 问题 1（严重）：品类维度静默丢失 139 笔订单、349,609.44 元

**现象**：`dws_trade_day`、`dws_store_day`、`dws_channel_day` 的 GMV 合计都等于
36,116,687.06，唯独 `dws_category_day` 只有 **35,767,077.49**，差 **349,609.57 元（0.97%）**。
按天对比发现 366 天里有 **189 天**对不上，且**每一天都偏小**——不是某天脏数据，是系统性的。

**根因**：品类汇总用 `JOIN dwd_order_item_clean` 关联明细来分摊实付金额。但有 139 笔订单，
它们的明细在清洗阶段被**整单剔除**了（抽样发现唯一一条明细的 `unit_price = -8009.64`，
负价，属脏数据）。订单本身有效、`pay_amount` 为正，却因为没有明细行而无法归属任何品类，
在 `inner join` 时被整笔丢掉。

**影响**：这不是"少了几块钱"，而是**品类结构分析从根上偏了**：
- 大屏"品类构成"饼图各品类占比之和不足 100%；
- `KPI_TOP_CATEGORY_SHARE`（第一大品类占比）的分母不含这 0.97%，占比被高估；
- 任何"按品类算总账"的交叉验证都会差 0.97%，且很难看出来。

**修复**：`sql/dws/50_build_dws_multi.sql` 改为 `UNION ALL` 两支：
有明细的订单按标价权重分摊；明细为空的订单归入 **「未知品类」**，金额单独成行。

```sql
-- 2) 明细为空的订单：金额归入「未知品类」，不静默丢弃
SELECT o.order_date AS dt, '未知品类' AS category, o.order_id,
       0 AS item_qty, o.pay_amount AS gmv
FROM ydsh_dwd.dwd_order o
LEFT JOIN (SELECT DISTINCT order_id FROM ydsh_dwd.dwd_order_item_clean) i
       ON o.order_id = i.order_id
WHERE i.order_id IS NULL
```

**结果**：`dws_category_day` 从 2,927 行变为 **3,043 行**（多出 116 个"日期 × 未知品类"组合），
GMV 合计回到 **36,116,687.06**，与全站完全一致。

**为什么选"未知品类"而不是"剔掉不报"**：剔掉等于让 0.97% 的生意在报表里不存在；
单列一个"未知品类"既保住了总量可对账，又让"有 0.97% 的订单无法归类"这件事
**在图上就能看见**——这是数据质量问题的正确暴露方式，而不是掩盖方式。

### 问题 2（中等）：先分组取整再相加，累积出 0.13 元舍入漂移

修完问题 1，品类汇总变成 36,116,686.93，还差 **0.13 元**。原因是原写法
`ROUND(SUM(...), 2)` 在每个"日期 × 品类"分组上取整，3,043 个分组各舍入一次，
误差累积成 0.13 元。

**修复**：存储层不做取整（`SUM(gmv) AS gmv`），取整交给展示层。
存储表保持**可加性**：`sum(分组) == 总量`。这是一条通用原则——
**汇总表里存四舍五入后的值，等于给下游埋了一颗对账永远差几分的雷**。

### 问题 3（部署）：应用容器没拿到 MySQL 口令，三引擎对账直接连不上

`docker-compose.yml` 里给 `app` 服务注入了 Hive 与 ClickHouse 的连接参数，
唯独漏了 MySQL。运行时报
`(1045, "Access denied for user 'root'@'172.18.0.3' (using password: NO)")`。

**修复**：补 `MYSQL_HOST / MYSQL_USER / MYSQL_ROOT_PASSWORD`，仍走
`${MYSQL_ROOT_PASSWORD:?}` 语法——缺变量就启动失败，不给默认值。

**这条的教训**：容器 `healthy` 只看它自己的健康检查，**不代表它拿到了全部依赖的凭据**。
S9 的端口探测全部通过，S8 却连不上库——所以"端口通"和"能干活"是两件事，必须分开验。

## 三、核对脚本自己写错的四处（也记录下来）

联调报告如果只写"系统有问题、我修好了"，是不完整的。这次有 4 条断言其实是**校验器写错**，
误报了系统：

| 误判 | 真相 | 修正 |
|---|---|---|
| `/api/health` 期望 `{"status":"ok"}` | 接口返回的是 `{"ok":true}` | 判据改为兼容两种字段 |
| 大屏门店序列取 `dash["store"]` | 实际键名是 `store_rank` / `store_scatter` | 改为分别校验 15 条排行 + 52 条散点 |
| NL2SQL 取 `rows[0][0]` 当数值 | `run_sql` 沿用第 3 周文本协议，`rows[0]` 是**表头** | 改取 `rows[1]`，并按 `\t` 切分 |
| ODS 总行数写成 115,809 | 实际 114,809（手算多加了一千） | 以 CSV 物理行数为准重算 |

**为什么值得写进报告**：校验器出错时会给出"系统坏了"的假信号，比不校验更危险——
它会让人去改本来正确的代码。所以**校验器本身也要有期望值来源**，
不能凭记忆写常量。这一条已经写进脚本注释和 AI 协同日志。

## 五、应用层联调结果

### 5.1 预测模型（第 3 周产物复检）

| 指标 | 随机森林 | 基线（近 7 日均值） | 判定 |
|---|---|---|---|

7 天预测均值 97,203 元，相对历史均值 98,679 元仅偏移 **1.50%**，无漂移。
**说明**：本次联调校验的是预测**产物与指标**，未重跑训练——运行时镜像不装
`scikit-learn`（约 200 MB），为演示引入这么大的依赖不划算。复现命令单独写在部署手册里。

### 5.2 NL2SQL 问答

提问「2024 年 6 月的 GMV 是多少？」，链路耗时 **4.2 秒**：

```sql
SELECT ROUND(SUM(gmv), 2) AS gmv_june
FROM ydsh_dws.dws_trade_month
WHERE month = '2024-06'
LIMIT 200
```

返回 **2,829,996.31**，与手工核算一致（`dws_trade_month` 中 `2024-06` 行的 gmv）。
模式识别为「大模型」，校验器通过（单条 SELECT / 表名白名单 / 已自动加 LIMIT）。

### 5.3 可视化与部署

- 取数 API `/api/kpi` 返回 GMV 36,116,687.06，与 Hive ADS 一致；
- 大屏序列完整：月度 12 条、品类 8 条、省份 15 条、门店排行 15 条、门店散点 52 条；
- 本地 `echarts.min.js` 1.03 MB 具在，断网也能演示；
- 6 个服务端口从应用容器内部反向探测全部连通，Superset `/health` 返回 `OK`。

## 七、结论

1. **端到端链路可跑通、可复现**：一条命令 `python verify_e2e.py` 即可在 30 秒内
   完成 67 项核对，0 失败。
2. **多口径已收敛**：ODS → DWD → DWS → ADS → MySQL → ClickHouse → 可视化，
   七个位置同值 36,116,687.06。
3. **联调的价值在于发现了单环节验收发现不了的问题**：34.96 万元的品类口径缺口
   藏了整整两周，只有在"全站 vs 品类"的交叉求和里才现形。
4. **校验器自身也要被校验**：4 条误判提醒我们，期望值必须有来源，不能凭记忆。

## 三、高频提问与参考回答

**Q1：为什么贴源层字段全用 STRING？**
A：贴源层原则是"原样落地、不做任何加工"。脏数据的典型表现就是类型不合法（如 age=200、price=-626.74），如果建表时就强转类型，异常值会直接导致导入失败或静默变 NULL，问题被掩盖。先在 STRING 层保留原始痕迹，把转换放到 DWD 层并配合校验，才能做到"问题可发现、可追溯"。

**Q2：年龄为什么用中位数填充，而不是均值？**
A：原始 age 字段含 200、-3 这类异常值，均值会被明显拉偏。中位数对异常值稳健；而且我们统计中位数时已经先过滤了 [1,120] 区间，等于先用业务规则剔除异常再取统计量。另外年龄分布通常右偏，中位数比均值更接近"典型用户"。

**Q3：邮箱为什么允许保留空值？**
A：邮箱是弱依赖字段，不参与订单、行为、销售等核心指标计算。臆造邮箱会污染后续用户画像和触达场景（可能给虚构地址发营销邮件）。所以采用"保留空值 + `email_flag` 标记位"，让下游按需过滤，而不是在源头造假。

**Q4：怎么区分"整行重复"和"主键重复但内容不同"？**
A：整行重复是采集端重复投递，10 个字段完全一致，直接保留一条即可，无信息损失。主键重复但内容不同，说明同一订单有多次记录（例如状态变更、金额修正），这时不能随机丢，要按 `order_date + order_time` 倒序取最新，保留的是"业务上最有效"的版本。两者用 `COUNT(*) - COUNT(DISTINCT 全字段拼接)` 与 `COUNT(*) - COUNT(DISTINCT 主键)` 分别量化。

**Q5：为什么去重用的是 ROW_NUMBER 而不是 DISTINCT？**
A：`DISTINCT` 只能处理"完全相同"的行，且无法控制保留哪一条。`ROW_NUMBER() OVER(PARTITION BY order_id ORDER BY ...)` 能精确指定保留规则（按时间取最新），且能一次性输出整行，是订单类去重的标准写法。

**Q6：Hive 里为什么不写 UPDATE？**
A：Hive 是写时模式（schema on write）的批处理系统，底层是 HDFS 上的不可变文件，不支持行级更新。即使开启 ACID 事务表，代价也很大。正确做法是"读旧表 → 生成新表"（`INSERT OVERWRITE` / `CREATE TABLE AS SELECT`），这也是数仓分层 ETL 的常规形态。

**Q7：数据质量五个维度里，你们认为哪个最重要？为什么？**
A：从本项目看是**唯一性**。订单重复会直接让 GMV、订单量、客单价三个核心指标同时虚高，且这种错误"看起来很正常"，不会报错，最难被发现。缺失值和格式问题通常一眼可见，重复值则需要专门统计才能暴露。

**Q8：如果数据量从 11 万涨到 11 亿，方案要怎么改？**
A：① 存储从本地文件系统换成 HDFS/S3；② 计算引擎从 Hive on MR 换成 Hive on Tez/Spark 或直接上 Spark SQL；③ 分区表按 `dt` 分区 + 分桶，避免全表扫描；④ 去重改用 `MERGE` 或增量去重（只处理增量分区）；⑤ 质量检查做成调度任务里的断言（如 Great Expectations），而不是事后人工跑 SQL。

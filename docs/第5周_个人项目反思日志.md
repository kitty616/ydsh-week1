## 二、技术维度

### 2.1 最扎实的三件事

**① 口径意识：先定义，再计算**

第一周我以为"销售额"就是"把金额加起来"。第二周才发现，明细表的 `unit_price` 是**标价**，
按它汇总得到 6.17 亿，而订单实付只有 3,611 万——**差 17 倍**。如果先算数再对口径，
这个错会一路传到仪表板上，而且看起来完全正常。

后来我养成了一个习惯：任何指标先写清"分子是什么、分母是什么、从哪张表来"，
写进《指标定义文档》，再写 SQL。第 3 周的 10 个 KPI 全部按这个流程做，
所以到第 5 周联调时，指标层一次就过。

**② 可加性：汇总表不能在存储层取整**

修完品类口径后，总量还是差 0.13 元。查下来是 `ROUND(SUM(...), 2)` 在 3,043 个分组上
各舍入一次，累积成 0.13 元。改成存储不取整、展示层取整后，`sum(分组) == 总量` 立刻成立。

这是一个很小但很本质的认知：**汇总表的价值在于"可加"，一旦破坏可加性，
下游所有对账都会差几分钱，而且永远说不清是谁的错。**

**③ 优化要看执行计划，不能看秒表**

第 4 周做压测时，我最初用耗时对比"分区裁剪 vs 全表扫描"，结果两条 SQL 都是 1 秒多，
看起来"分区没用"。后来用 `EXPLAIN DEPENDENCY` 数分区才发现：分区裁剪确实只读了 1 个分区，
只是 1.4 万行的数据量下，Tez 每次约 0.5 秒的容器启动开销把扫描差异完全盖住了。

同一时期我还验证了一件事：Hive 4 默认 `hive.auto.convert.join=true`，
维表 15 行会自动转 MapJoin，**手写 `/*+ MAPJOIN */` 前后执行计划一模一样**。
这打破了我"教程里的调优手段都该加上"的惯性——**加之前先看计划，否则只是心理安慰。**

### 2.2 还需要加强的两件事

**① 对"看起来正常"的警惕不够**

0.97% 的品类口径缺口藏了整整两周。它不报错、不抛异常、报表照常出，只是品类加起来
比全站少一点点。我是因为第 5 周写了"每个维度独立求和"的交叉对账才发现的。

反思：第 3 周做 ADS 层时，如果每个指标表都做一次"求和 = 总量"的自检，
这个问题当场就会暴露。**以后建汇总表，必须同时写一条对账 SQL，不能只写建表语句。**

**② 前端调试能力偏弱**

Superset 的交叉筛选配了三处（`emitCrossFilters`、作用域、特性开关），用真实鼠标点柱子
仍然只弹 tooltip。我最后停在"记录现象"，没有继续往下查前端源码。
这是一个明确的能力短板：**面对打包后的前端产物，我的排查手段只有 grep 关键字，缺少
系统性定位方法。**

## 三、协作维度

这是单人项目，所以"协作"主要是**我和工具、我和未来的自己**之间的协作。

### 3.1 做得好的：把决策写进注释

代码里我坚持写"为什么"，而不是"做什么"。比如 compose 里那段：

```yaml
# 卷挂在 /opt/hive/data/warehouse：与 hive-site.xml 的 hive.metastore.warehouse.dir
# 以及 Metastore 中已登记的 table LOCATION 完全一致。
# 之前挂在 /user/hive/warehouse，导致容器重建后元数据路径与真实文件路径错位。
```

第 5 周回头看这些注释，几乎每一条都救了我一次——因为**报错信息和根因往往隔了三层**，
注释是唯一能跨周传递上下文的东西。

### 3.2 做得不好的：分支纪律是补的，不是一开始就有的

前两周我直接在 `main` 上提交，到第 3 周做 Git 协同时才补了 `feature/*` 分支和 PR 流程。
结果是前期的历史是一条直线，后期才出现分支和合并节点，**看图就知道规范是后来补的**。

第 5 周我特意把全部工作放在 `feature/week5-integration` 上，用 `--no-ff` 合并，
让这一次的合并节点在图上真实可见。**规范不是写在文档里的，是写在提交图里的。**

### 3.3 一个具体的教训：注释里的口令

`tools/shot.js` 的用法注释里，我写了 `--login admin:真实口令` 做示例，被安全扫描抓出来。
改掉文件只是止血——**只要进过 `git log`，正确做法就是轮换口令**，而不是 `git commit --amend`
抹痕迹。这件事让我明白：**"提交前自查"不是形式，是必须执行的步骤**，
所以现在提交前固定跑两条命令：

```bash
git ls-files | grep -i env
git log -p --all -S "sk-"
```

## 四、表达维度

### 4.1 答辩：从"我做了什么"到"这意味着什么"

第一次写答辩提纲（第 2 周），我列的是"我建了 4 张表、写了 3 个脚本"。
第 5 周重写时，我把它改成"0.97% 的钱去哪了"这样的叙事：现象 → 定位 → 根因 → 修复 → 教训。

差别在于：**前者是工作量清单，后者是判断力展示。** 评委不会因为"你写了 3 个脚本"给分，
但会因为"你能自己发现并修掉一个藏了两周的口径 bug"给分。

### 4.2 文档：从"记录过程"到"支撑决策"

《数据质量清洗报告》第 2 周版本只写了"修了什么"，第 5 周补了两块：

- **订单完整率 99.03%**：不只统计"修了多少行"，还统计"清洗后还有多少订单是完整可分析的"；
- **为什么缺失值只修 45.33%**：明确写出"邮箱是弱依赖字段，编造比留空更危险"。

**一份好文档不是把做过的事列一遍，而是让读者能据此做决定**——比如看到 99.03% 这个数，
就知道该不该去查那 139 笔订单。

### 4.3 还要练的：控制时间

10 分钟要讲完 5 周内容，我第一版提纲写了 24 页，砍到 16 页才勉强够。
砍的过程很痛苦，但也逼我想清楚"哪三件事非讲不可"：
**一个数对到底（一致性）、一个坑怎么发现的（判断力）、一条命令能不能起来（工程化）。**

## 五、如果重做一次，我会改什么

| # | 改动 | 原因 |
|---|---|---|
| 1 | 第 1 周就建 `feature/*` 分支和约定式提交 | 规范后补的痕迹在图上一眼可见 |
| 2 | 每建一张汇总表，同时写一条"求和 = 总量"的对账 SQL | 0.97% 的缺口就是因为缺这一步 |

| 5 | 密钥用 `.env` + 启动校验，从第一个提交开始 | 口令进过历史，只能轮换不能抹 |

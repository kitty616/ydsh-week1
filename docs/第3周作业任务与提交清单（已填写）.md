## 一、本周任务详细化

本周从"把数据洗干净、建好四层"进入"把数据用起来"：先建 DWS 汇总层与 ADS 应用层把 KPI 算准，再用 Python 做时间序列分析与预测建模，随后接入大模型 API 构建 NL2SQL 问答能力，最后让 AI 参与洞察生成并对它的产出做批判性验证。全程用 Fork + PR + Code Review 的团队流程承载变更。

### 子任务 1：DWS / ADS 层建设与 KPI 指标计算（2 课时）

**任务目标**：按天/周/月、品类、门店、渠道等维度汇总订单金额、订单量与用户数，并面向业务场景输出应用层表。

**操作步骤**：
① 先定口径再写 SQL——GMV 是否含取消单、客单价分母用订单还是用户、品类 GMV 如何分摊，这些判断写进《指标定义文档》作为唯一口径；
② DWS 建 7 张表：`dws_trade_day` / `dws_trade_week` / `dws_trade_month` / `dws_category_day` / `dws_store_day` / `dws_channel_day` / `dws_user_stat`；
③ ADS 建 5 张表：`ads_kpi_core`（10 项核心指标）/ `ads_monthly_trend` / `ads_sales_daily_report` / `ads_category_topn` / `ads_user_segment`（RFM 分层）；
④ 每张汇总表末尾内置对账查询，与订单事实表比 GMV。

示例（品类 GMV 的分摊，必须按明细占比摊到订单）：

```sql
SELECT t.category,
       SUM(o.pay_amount * t.item_amt / t.order_amt) AS category_gmv
FROM dwd_order o
JOIN (SELECT order_id, category,
             SUM(quantity * unit_price * (1 - discount)) AS item_amt,
             SUM(SUM(quantity * unit_price * (1 - discount))) OVER (PARTITION BY order_id) AS order_amt
      FROM dwd_order_item GROUP BY order_id, category) t
  ON o.order_id = t.order_id
GROUP BY t.category;
```

**产出物**：`sql/dws/`、`sql/ads/` 目录脚本 + 《指标定义文档》。
**验收标准**：分层合理、指标计算正确。**实测**：12 张表建成；日/周/月/门店/渠道五个口径 GMV 与事实表完全一致（均 36,116,687.06 元）。

### 子任务 2：时间序列分析与预测建模（2 课时）

**任务目标**：从 Hive 读取日 GMV 序列，完成趋势分解、移动平均、同比/环比，并用 sklearn 预测未来 7 天。

**操作步骤**：
① 从 ADS 导出 366 天日序列到 `data/daily_gmv.csv`；
② `ts_decompose.py`：三条移动平均（7/14/30）、STL 分解（周期 7）、月环比 MoM、周环比 WoW，并显式检查同比是否可行；
③ `ts_forecast.py`：构造 lag7/14/21、ma7/14/30 与日历特征，**刻意不用 lag1**（避免递归预测的误差累积），滚动留出最后 28 天做测试；
④ 三条朴素基线（上周同日 / 近 7 日均值 / 近 14 日均值）对照线性回归与随机森林；
⑤ 评估 MAE / MAPE / RMSE，并写清模型适用边界。

```bash
docker exec ydsh-hive-server beeline -u jdbc:hive2://localhost:10000/ydsh_ads \
  --outputformat=tsv2 -e "SELECT dt, gmv, order_cnt, user_cnt, aov FROM ads_sales_daily_report ORDER BY dt" \
  > data/daily_gmv.csv
python python/ts_decompose.py    # 分解 + 环比
python python/ts_forecast.py     # 建模 + 预测
```

**产出物**：《预测建模分析报告》、`python/ts_decompose.py`、`python/ts_forecast.py`、`data/forecast_7d.csv`。
**验收标准**：方法得当、评估完整、有边界分析。**实测**：STL 季节强度 0.2183、趋势强度 0.0859；最优模型 MAPE 11.55%（线性回归），相对近 14 日均值基线仅改善 5.6%。

### 子任务 4：NL2SQL 构建（2 课时）

**任务目标**：抽取 Hive Schema，基于 LangChain 构建"自然语言 → SQL → 执行 → 结果"链路，并用提示词约束 SQL 规范性。

**操作步骤**：
① `schema_extract.py` 读 Hive Metastore 生成表名/字段/注释，**只暴露 14 张业务表**（ods_* 原始层不暴露），并手工补业务语义（如 `province` 真实取值是"广东省"不是"广东"、数据日期区间）；
② 提示词写 10 条硬约束：表名白名单、禁 `SELECT *`、必须带分区过滤、别名用反引号、相对时间以数据最新日期为基准等；
③ `nl2sql.py` 直连版 + `nl2sql_chain.py` LangChain 版（结构化输出 + 三级降级 + 回调计时），两版共用校验器与执行器；
④ `test_guard.py` 做 SQL 静态校验器对抗测试；
⑤ 用 6 条典型问题验证，`--compare` 做两版 A/B 对照。

```bash
python python/schema_extract.py
python python/test_guard.py            # 17 条对抗用例
python python/nl2sql.py --batch        # 6 条典型问题
python python/nl2sql_chain.py --compare
```

**产出物**：`python/nl2sql.py`、`python/nl2sql_chain.py`、`python/schema_extract.py`、`python/test_guard.py`、`data/schema_prompt.txt`、《NL2SQL 设计与测试报告》。
**验收标准**：可用性、SQL 正确率、Prompt 设计。**实测**：真实模型下 6/6 全部生成、校验、执行成功；校验器 17/17 通过；A/B 两版执行成功 6/6、SQL 完全一致 1/6。

## 四、问题与解决

| 问题 | 原因 | 解决方式 | 是否 AI 有效解决 |
|---|---|---|---|
| `PERCENTILE` 报参数类型错误 | 第二参数被隐式解析为 decimal | 改用 `PERCENTILE_APPROX` 并显式 `CAST(... AS DOUBLE)` | 是 |
| 批量执行遇错不中断，误删已清洗表 | beeline `-f` 默认继续执行后续语句 | 清空中间表整链重跑；脚本改为可重复执行 | 是（需人工补幂等性设计） |
| 表重命名后找不到表 | `RENAME TO` 目标未写库名，落到 `default` 库 | 补库名前缀并移回 | 是 |
| 行为时间 6,088 条未转换 | 真实格式 `2024/11/05 15:49` 缺秒，与预想三种形态都不同 | 重新抽样确认真实形态，补「补 `:00`」分支 | 首版否，第二版是 |
| 清洗阈值重复执行会漂移 | 阈值从清洗结果表计算，每跑一次收窄一点 | 改为从贴源层 `ods_order` 计算，保证幂等 | 是 |
| 区域出现「重庆市-重庆」 | 直辖市 province 与 city 名称不等，等值判断失效 | 改为前缀匹配 `province LIKE CONCAT(city,'%')` | 是 |
| 类目销售额与订单总额差一个量级 | 明细 `unit_price` 是吊牌价，与订单实付价口径混用 | 按订单内明细占比分摊实付金额 | 是 |
| IQR 上界代码与文档口径不一致 | 代码写成 Q1 基准，注释与文档声明 Q3 基准 | 改代码为 Q3 基准，同步文档算术与阈值 | 由人工复核发现，AI 修正 |

**总体判断**：AI 在「按报错定位原因」和「按数据分布生成映射规则」两类任务上效率最高，本周 8 个环境/语法类问题基本一轮定位；但在**口径定义**（P99 还是 IQR、吊牌价还是实付价、删还是留）上不能交给它决定，这几处恰恰是本周返工最多的地方。

## 五、反思与总结

**AI 协同带来的价值**

1. 把「试错」的成本压到最低。四个清洗脚本、五个建模脚本、三份文档，一周内完成，其中大量时间花在验证而不是打字上。
2. 报错定位快。`ClassNotFoundException`、`Too many counters`、`No FileSystem for scheme "C"` 这类问题，描述清楚上下文后基本一次给出根因，省掉大量搜索。
3. 文档一致性维护。同一批数字要在报告、简报、周志、答辩提纲里出现几十次，靠人工抄容易不一致，交给 AI 批量同步可靠得多。

**AI 的局限与风险**

1. **会「编」出看起来合理的数字**。本次发现两处：一是阈值算式的乘法结果对不上（3,809.12 + 3×2,515.73 被写成 8,840.59）；二是答辩稿里「1.5 倍会多命中 400 多条」这类未经实测的推断。凡是要写进交付物的数字，必须回跑一遍。
2. **代码与注释可能各说一套**。IQR 那次，注释写 Q3 基准、代码写 Q1 基准，两边都「看起来对」。这类错误不跑不算发现不了。
3. **倾向于给一个漂亮结论**。若不加约束，它会倾向于把「四渠道各占 25%」解释成业务洞察，而不是指出这是模拟数据的生成缺陷。
4. **对环境状态没有记忆**。容器重启、表被改过结构，它并不知情，必须每次实际查一遍再下结论。

**本次协作中我的能力提升**

1. 学会了「先取数、再写规则」：枚举归并前先 `GROUP BY` 看真实值域，比照文档想象要可靠得多。
2. 建立了幂等意识：脚本重复执行结果必须一致，阈值必须来自不可变的上游。
3. 理解了统计量的适用边界：分位数在脏数据里天然不可靠，稳健统计量（IQR）才有意义。
4. 学会了质疑 AI 给出的算术：这次就是一句乘法复核，避免了一个答辩现场会被当场戳穿的错误。

**对 AI 协同的改进建议**

1. 让 AI 输出的每个数字都附「可复算的出处」（哪张表、哪条 SQL），而不是只给结论。
2. 涉及阈值、口径、删留这类判断，先让它列出 2–3 个方案和各自代价，由人拍板，而不是直接给一个「最佳实践」。
3. 代码与文档里的同一参数，改一处就要全链同步，最好由脚本生成文档中的数字而不是手写。

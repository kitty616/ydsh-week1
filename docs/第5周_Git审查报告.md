## 一、审查方法

```bash
git log --oneline --graph --all          # 整体形态
git log --pretty=%s                      # 提交信息全量
git branch -a --format='%(refname:short)' # 分支清单
git branch --merged main                 # 已合并分支
git tag -l                               # 标签
git shortlog -sn HEAD                     # 作者分布
git grep -nE "sk-[A-Za-z0-9]{16}|ydsh_ck_2026|Ydsh@2026" HEAD   # 当前敏感信息
git log -p --all -S "sk-"                # 历史中是否出现过密钥
```

审查不只看"现在对不对"，还看"历史里有没有留过坑"——**仓库的历史是公开的，
删文件不等于删历史**。

## 三、约定式提交符合度

### 3.1 分布

| 类型 | 数量 | 占比 | 说明 |
|---|---|---|---|
| `docs` | 28 | 40.6% | 文档是本项目的主要产出 |
| `feat` | 14 | 20.3% | 功能模块 |
| `fix` | 13 | 18.8% | 缺陷修复 |
| `refactor` | 1 | 1.4% | 重构 |
| `chore` | 1 | 1.4% | 杂项 |
| 合并提交 | 10 | 14.5% | 由 Git/平台自动生成或 `merge:` 前缀 |
| 其他 | 2 | 2.9% | 见 3.2 |

**规范率**：非合并提交 59 条中 **57 条符合约定式**，符合率 **96.6%**。

### 3.2 不规范的提交

| 提交信息 | 问题 | 是否整改 |
|---|---|---|
| `init: 第一周 ODS 层搭建（Docker + Hive 4.0.0）` | `init` 不是标准类型，应为 `feat(ods):` | 不整改：改写历史会改变已推送的 SHA，代价大于收益；记录在案 |
| `补:llm_ping 增加模型列表探测…` | 用了中文前缀，且一条提交混了两件事（功能 + 文档） | 不整改，同上；教训写入反思日志 |
| `merge: 并入 fork 上游的…` ×2、`Merge PR #…` ×2、`Merge pull request #…` ×3 | 合并提交未统一格式 | **部分整改**：第 5 周的合并改用 Git 默认的 `Merge branch 'xxx': 说明` 格式，并把说明写全 |

**为什么不用 `rebase -i` 把它们改漂亮**：历史是事实记录。为了评分好看而改写历史，
等于把"规范是后补的"这件事藏起来——**这比不规范本身更糟**。
正确做法是保留历史、如实记录、从下一次提交开始做对。

### 3.3 值得肯定的写法

以第 5 周的三条提交为例，它们符合"提交信息解释为什么"的标准：

```
fix(dws): 品类汇总补「未知品类」分支，修复 0.97% GMV 静默丢失

联调时发现 dws_category_day 合计 35,767,077.49，比全站少 349,609.57 元（0.97%），
366 天里 189 天都偏小，是系统性缺口而非脏数据。
...
选「未知品类」而不是剔掉不报：剔除等于让 0.97% 的生意在报表里不存在。
```

**判据**：只看标题能不能知道"改了什么"，看正文能不能知道"为什么这么改"。
两条都满足才算合格。

**问题**：8 个本地分支里只有 1 个是本周的，其余 7 个都是历史残留。
**规范做法**：合并后立即删除功能分支（`git branch -d`），需要留痕则打标签。

**为什么本周还要新建分支**：单人项目走分支不是形式主义——它让"这次改动是一个整体"这件事
在历史里可见，出问题时能整段回滚（`git revert -m 1 <merge>`），而不是逐个提交挑。

## 六、敏感信息审查

### 6.1 当前状态

```bash
$ git grep -nE "sk-[A-Za-z0-9]{16}|ydsh_ck_2026|Ydsh@2026" HEAD
docs/第4周_API配置指南.md:30:# DEEPSEEK_API_KEY=sk-xxxxxxxxxxxxxxxx
```

唯一命中是**占位符** `sk-xxxx`，不是真实密钥。其余扫描结果为空。

### 6.2 历史事件（必须记录）

第 4 周发现 `tools/shot.js` 的用法注释里写过 `--login admin:真实口令` 作为示例。
虽然发现后立即改成占位符，但**这行内容进过 `git log`**。

| 处理 | 做法 | 结论 |
|---|---|---|
| 错误做法 | `git commit --amend` / `filter-branch` 抹掉 | 未采用：改写已推送历史会破坏协作者仓库，且"抹掉"本身掩盖了问题 |
| 正确做法 | **轮换口令** + 记录事件 + 补检查步骤 | 已执行 |

**已固化的检查**：提交前固定跑两条命令，写进《部署手册》与《API 配置指南》：

```bash
git ls-files | grep -i env                  # 确认 .env 没被跟踪
git log -p --all -S "sk-" | head            # 确认历史里没有真 Key
```

### 6.3 密钥管理机制

- 所有口令走 `.env` + `${VAR:?}` 语法，缺变量 `docker compose up` 直接失败；
- `.env` 在 `.gitignore` 与 `.dockerignore` 双排除，镜像里不含；
- 代码里**没有默认口令**（第 5 周专门清理了 `bench_query.py` 里的 `"ydsh_ck_2026"` 与 `"root"` 默认值）。

## 七、提交身份问题（本次审查新发现）

```bash
$ git log --format="%an <%ae>" | sort | uniq -c
     57 quxinfeng <kitty616@users.noreply.github.com>
     12 kitty616  <1842147404@qq.com>
```

同一个人在两个环境下用了两个 `user.email`，导致：

- GitHub 贡献图只统计其中一个邮箱，**12 次提交在图上是"别人"的**；
- `git shortlog` 显示两个人，看起来像协作项目。

**处理**：新增 `.mailmap` 做身份映射，**不改写历史**：

```
quxinfeng <kitty616@users.noreply.github.com> <1842147404@qq.com>
```

生效后 `git shortlog -sn` 从两行合并为一行（69 次提交）。同时把本仓库的
`user.email` 统一为 noreply 邮箱，避免后续再分叉。

**为什么用 mailmap 而不是 rebase**：mailmap 只影响展示层（`shortlog` / `blame` / `log`），
零风险；改邮箱要重写全部历史提交的 SHA，会破坏标签与远端。

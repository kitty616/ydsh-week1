## 一、先把 13 个东西串成一句话

浏览器里 6 个页面，Docker 里 7 个容器。合起来是 13 个"部件"，但只需要一句话就能讲清关系：

> **页面是给人看的脸，容器是干活的手。页面上没有一个数字是写死的——每个数字都能顺着容器找回到一张表。**

这句话是整场演示的根。老师后面无论从哪个页面问"这个数哪来的"，答案都是同一条路径：页面 → 接口 → 服务层表 → 汇总层 → 明细层 → 原始 CSV。

所以下面的讲法不是"一个页面一个页面介绍功能"，而是**每打开一个页面，就往下指一层**。

## 二、Docker 里的 7 个容器

### 2.1 它们不是平行的，是一条有严格顺序的链

```
mysql (3307)
  └─ healthy ──▶ hive-metastore (9083)
                   └─ healthy ──▶ hive-server (10000 / 10002)
                                    ├─ healthy ──▶ clickhouse (8123 / 9000)
                                    │                └─ healthy ──▶ app (8501) ──▶ api (8000)
                                    └─ healthy ──▶ superset (8088)   ← 同时等 mysql healthy
```

这条链不是画着好看的。`docker-compose.yml` 里每一处依赖都写的是 `condition: service_healthy`，不是普通的 `depends_on`。

**这两者差别很大**：`depends_on` 只保证"容器起来了"，而 Hive 的容器起来之后还要几十秒才真正能连；`service_healthy` 会一直等到健康检查通过才开始下一个。所以每个服务的 `start_period` 给得不一样：`mysql` 30 秒、`hive-metastore` 60 秒、`hive-server` 和 `superset` 都是 90 秒——冷启动越慢的服务，余量留得越大。

> **台词**：如果只写 `depends_on`，你 `docker compose up -d` 之后 `docker ps` 全绿，但 Superset 一打开就报连不上 Hive。因为它"起来了"，但没"准备好"。这两个词差着一分半钟。

### 2.2 七个容器分别干什么

| # | 容器 | 镜像 | 端口 | 职责 |
|---|---|---|---|---|
| 1 | `ydsh-mysql` | `mysql:8.0` | 3307 → 3306 | Hive 元数据库 `metastore` + Superset 元数据库 `superset` + 服务层结果表 `ydsh_ads` |
| 2 | `ydsh-hive-metastore` | `apache/hive:4.0.0` | 9083 | 存"表在哪、字段是什么"；数据本身在 `hive_warehouse` 卷的本地目录里（这套单机环境没上 HDFS） |
| 3 | `ydsh-hive-server` | `apache/hive:4.0.0` | 10000（JDBC）/ 10002（Web UI） | 干重活：四层建模、多表关联、全量汇总 |
| 4 | `ydsh-clickhouse` | `clickhouse/clickhouse-server:24.8` | 8123（HTTP）/ 9000（Native） | 干快活：同一份 ADS 结果列存，交互查询秒回 |
| 5 | `ydsh-superset` | `ydsh/superset:4.1.1`（本地构建） | 8088 | BI 看板，8 张图表挂 3 个数据源 |
| 6 | `ydsh-app` | `ydsh/app:4.1`（本地构建） | 8501 | Streamlit 对话式问答，NL2SQL 闭环 |
| 7 | `ydsh-api` | `ydsh/app:4.1`（**同一镜像**） | 8000 | 大屏取数接口 `/api/dashboard.json` |

三个数字值得单独点出来：

- **端口是 3307 不是 3306**：宿主机上已经装了本机 MySQL80 服务，占着 3306。容器内部仍然是 3306，所以 Hive 的 `jdbc:mysql://mysql:3306` 一个字都不用改，只有从 Windows 用客户端连的时候才写 3307。
- **`app` 和 `api` 是同一个镜像**：`docker images` 里只有一条 `ydsh/app:4.1`。api 容器只是把启动命令换成了 `python app/api_server.py`。同一个镜像跑两个入口，省一次构建，也保证两边读的是同一套代码。
- **四个命名卷**：`mysql_data`、`hive_warehouse`、`clickhouse_data`、`superset_home`。`docker compose down` 之后数据还在，只有 `down -v` 才会真的清空。

### 2.3 七个"只有自己搭过才知道"的细节

这一节是整场演示里最容易加分的地方。不是因为难，而是因为**每一条都是踩过坑之后改的**，改的痕迹还留在 compose 的注释里。

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | Hive 启动报 `ClassNotFoundException: com.mysql.cj.jdbc.Driver` | 官方 `apache/hive:4.0.0` 镜像**没内置** MySQL 驱动 | 把 `lib/mysql-connector-j-8.0.33.jar` 单文件挂进 `/opt/hive/lib/` |
| 2 | 容器重建后表能查到、数据读不出来 | warehouse 原来挂在 `/user/hive/warehouse`，与元数据里登记的 `LOCATION` 不一致 | 统一挂 `/opt/hive/data/warehouse`，和 `hive-site.xml`、Metastore 里登记的三处对齐 |
| 3 | 质量评估 SQL 报 `Too many counters: 121 max=120` | Tez/MR 默认计数器上限 120，`10_quality_assessment.sql` 一次跑超了 | 挂载自己的 `hive-site.xml`，上限调到 4000 |
| 4 | ClickHouse 健康检查老是失败 | 带密码的探测语句容易因为引号和转义出错 | 改用 `/ping`，这个端点免认证，最稳 |
| 5 | Superset 连不上 Hive / MySQL | 官方镜像缺 `pyhive` 和 `pymysql` 两个驱动 | 本地写 Dockerfile 补上，打出 `ydsh/superset:4.1.1` |
| 6 | 口令散落在 compose 里 | 明文进版本库 | 全部改成 `${VAR:?提示}`，`.env` 里缺一项就直接启动失败，不退化成一个"看起来能跑"的默认值 |
| 7 | 初始化脚本重复执行会不会建两遍 | 人工点鼠标建看板不可复现 | `provision.py` 只读挂载、写成幂等，重复跑只会覆盖不会重复 |

> **台词**：这七条里，前三条是"容器能起来但用不了"，后四条是"能用了但别人复现不出来"。我花在第二类上的时间比第一类多——因为一个只在你这台机器上能跑的东西，等于没做完。

## 三、六个页面，逐个讲

打开顺序就是下面这个顺序，从"老板看的"到"工程师看的"。

### 3.1 第一页 · 经营分析大屏（`http://127.0.0.1:8010/`）

**屏幕上是什么**：深色底。顶部六个 KPI（GMV 3611.67 万元、订单 14,398、客单价 2508.45、活跃用户 1,000、取消率 14.05%、整体折扣率 11.77%），下面六张 ECharts 图（月度成交趋势、下单时段 × 品类热力、品类销售构成、区域分布、门店经营质量、支付方式占比），右下角还有一个门店 GMV 排行 Top10 榜单——那个不是图，是 HTML 列表。

**背后是谁**：`ydsh-api` 容器。页面是纯静态 HTML + ECharts，打开时 `fetch` 一次 `http://127.0.0.1:8000/api/dashboard.json`，拿到数据再画图。

**这一页最该讲的三件事**：

1. **页脚自己会交待数据从哪来。** 右下角那行写的是 `实时接口` 还是 `内嵌快照`——接口通就显示前者，不通回落到 `data/dashboard.js` 的离线快照并显示后者。**我没有让它悄悄回落**，因为"这张图是算出来的还是昨天存的"这件事，看的人有权知道。

2. **页脚的数据时点写的是 2026-11-17 08:42，不是此刻。** 这一点必须说清楚：`/api/dashboard.json` **不是每次请求都去查 Hive**，它读的是 `export_dashboard_data.py` 从 Hive 导出的一份快照，按文件 mtime 做缓存，文件更新了自动重载。所以"实时"这两个字指的是**走的是接口而不是读本地文件**，不是"毫秒级实时"。

3. **为什么不实时查。** 大屏要的是"推开就亮"，而每次刷新都全量查 Hive 要好几秒——6 个 KPI 加 6 张图，背后是 DWS 六个维度表的聚合。演示场景不需要秒级时效，用导出快照换打开速度，这个取舍是明写的，不是藏着。

> **台词**：这一页是给业务看的。请老师注意右下角那行小字，写着"实时接口"——意思是这份数据是通过 HTTP 接口拿的，不是读本地文件。但我得补一句实话：**接口背后读的是上次从 Hive 导出的快照，数据时点就写在那儿，11 月 17 日。** 我没做成每次刷新都去查 Hive，因为那样打开要好几秒；大屏要的是"推开就亮"，不是"最新到秒"。

### 3.2 第二页 · Superset 运营驾驶舱（`localhost:8088/superset/dashboard/ydsh-week4-ops/`）

**屏幕上是什么**：左侧筛选栏（月份，12 个选项），右侧 8 张图表——①日 GMV 趋势、②月度 GMV 分布、③月度 GMV 趋势、④品类销售柱状图、⑤门店 GMV 排行 Top10、⑥省份 GMV 分布、⑦支付方式占比、⑧用户价值分层。

**背后是谁**：`ydsh-superset` 容器。它的元数据（数据源、数据集、图表、看板定义）存在 `ydsh-mysql` 的 `superset` 库里，业务数据来自三个源：

| 数据源 | 数据集数 | 举例 |
|---|---|---|
| Hive 数仓 (ydsh_ads) | 5 | `ads_sales_daily_report`、`ads_store_rank`、`ads_user_segment` |
| MySQL 服务层 (ydsh_ads) | 4 | `monthly`、`region`、`pay_type`、`sales_daily` |
| ClickHouse 加速层 (ydsh_ads) | 2 | `sales_daily`、`trade_monthly` |

**这一页该讲的是"一份数据、三种读法"**：同一份日销售结果，Hive 里叫 `ads_sales_daily_report`，MySQL 和 ClickHouse 里叫 `sales_daily`——表名不同，但口径必须是同一个。这不是巧合，是第 5 周联调专门验的（7 个环节收敛到同一个 36,116,687.06）。

**还要主动说一件事**：数据源列表里能看到 4 条，但真正在用的是 3 条。id=1 的「Hive 数仓（ydsh_ads）」是第 4 周调试时用全角括号重复建的，名下 0 个数据集、0 张图表，是个孤儿条目。**不主动说，被翻出来就是"数据源都管不清"；主动说了，就是"我知道它在那儿但没图引用它"。**

> **台词**：这个看板是第 4 周做的，8 张图挂 3 个数据源。老师可能会看到数据源有 4 个——第 1 个是我调试时重复建的，全角括号和半角括号之差，名下没有任何图表引用。要清掉一条 SQL 就行，但我不想在演示前动元数据库。

### 3.3 第三页 · 智能经营问答（`localhost:8501/`）

**屏幕上是什么**：左侧「运行状态」——Hive 数据源绿灯、`可用（0.087s）`、接入方式 `pyhive`、目标 `hive-server:10000`；大模型绿灯「已配置」。下面 5 个示例问题，右侧是对话区。

**背后是谁**：`ydsh-app` 容器（Streamlit + 第 3 周的 `nl2sql.py` 内核）。

**这一页该讲的是"为什么它不会瞎编"**：

- 它生成的是 **Hive SQL**，不是自然语言答案。SQL 会显示在界面上，老师可以逐字看。
- SQL 跑在**四层数仓的 ADS/DWS 上**，不是直接查原始表。
- 大模型只负责"把中文翻成 SQL"，**不负责算数**。算数的是 Hive。

> **台词**：这一页最容易让人误会——以为是大模型在回答。不是。大模型只做一件事：把"2024 年 6 月的总 GMV 是多少"翻译成一条 SQL。这条 SQL 会明明白白显示出来，然后交给 Hive 去跑。**翻译错了我能看出来，算错了是 Hive 的事，跟模型无关。** 这就是为什么我要把 SQL 摆在界面上，而不是只给一个答案。

### 3.4 第四页 · ClickHouse 查询台（`localhost:8123/play`）

**屏幕上是什么**：一个极简的 SQL 输入框。已经填好密码和一条语句，点 Run 直接出结果：**366 行 / 36,116,687.06 / 耗时 0.013 秒**。

**背后是谁**：`ydsh-clickhouse` 容器。

**这一页的作用是"当面对账"**：老师在任何地方看到过一个 GMV，这里可以现场再算一遍。0.013 秒这个数字也不是装饰，第 4 周压测记录里同样一个查询：

| 引擎 | P50 | P95 | QPS |
|---|---|---|---|
| Hive | 850.8 ms | 1247.7 ms | 4.17 |
| ClickHouse | **7.1 ms** | **10.7 ms** | **924.83** |

按延迟算是 **120 倍左右**（850.8 ÷ 7.1）。QPS 那一列悬殊更大，但两边并发数不同（Hive 4、ClickHouse 8），严格说不能直接相除——这也是为什么我在文档里一直用延迟说事，不用 QPS 说事。

> **台词**：这一页我只想说一件事：0.013 秒。同样一个求和，Hive 要 800 多毫秒，ClickHouse 要 7 毫秒，差 120 倍。所以架构里 Hive 干重活、ClickHouse 干快活——不是我喜欢多搭一套，是交互式查询等不了那 800 毫秒。

### 3.5 第五页 · HiveServer2 监控台（`localhost:10002/`）

**屏幕上是什么**：Active Sessions / Open Queries / Last Max 25 Closed Queries 三张表。

**背后是谁**：`ydsh-hive-server` 容器自带的 Web UI。

**这一页的作用不是看数据，是看"它真的在干活"**：在第三个页面问一次 NL2SQL，或者跑一次 beeline，这里的 Closed Queries 就会多一行，带延迟时间。演示时这一页可以不讲，但**如果老师怀疑"你是不是查的缓存"，切到这一页再跑一条新 SQL，这里会当场多出一条记录**。

> **台词**：这一页是 Hive 自己的日志面板。刚才那条查询跑完之后，这里会多一行，带真实延迟。这是个旁证——证明数是当场算的，不是提前摆好的。

### 3.6 第六页 · 取数 API（`localhost:8000/`）

**屏幕上是什么**：三个链接——`/api/dashboard.json`、`/api/kpi`、`/api/health`。

**背后是谁**：`ydsh-api` 容器（和 Streamlit 同一个镜像，只是入口不同）。

**这一页要讲"接口返回什么"**：点 `/api/kpi`，返回的是

```json
{"gmv": 36116687.06, "order_cnt": 14398, "aov": 2508.45,
 "active_user": 1000, "cancel_rate": 0.1405,
 "discount_rate": 0.1177, "repurchase_rate": 1.0, "top_category_share": 0.1495}
```

八个字段，对应大屏上六个 KPI 加两个占比。**大屏上的每一个数字，都能在这里找到出处。**

> **台词**：这一页是最不"好看"的一页，但它是最关键的一页。大屏是壳，这一页才是数据出口。老师如果问"大屏那个 3611.67 万从哪来"，答案就在这行 JSON 里：36,116,687.06 元，除一万，四舍五入到两位，就是 3611.67 万。

## 六、九个可能被问的问题

**Q1｜七个容器是不是过度设计？一个 Python 脚本也能算。**
一个脚本能算，但算完之后没法给别人用。七个容器分别解决"存得住"（mysql 卷）、"算得动"（hive）、"答得快"（clickhouse）、"看得见"（superset / app / api）。真要合并，最省也能压到三个：mysql + hive + 一个前端。但拆开之后每一层都能单独替换——比如把 Hive 换成 Spark，只动一个容器。

**Q2｜MySQL 为什么映射 3307？是不是配错了？**
不是。宿主机 3306 被本机装的 MySQL80 服务占着。容器内部还是 3306，所以 Hive 的 JDBC 串一个字没改；只有从 Windows 用客户端连的时候写 3307。这是刻意的，注释就在 compose 第 21 行。

**Q3｜数据存在容器里，`docker compose down` 会不会全丢？**
不会。四个命名卷：`mysql_data`、`hive_warehouse`、`clickhouse_data`、`superset_home`。`down` 只删容器不删卷，`down -v` 才真删。这个可以演示，但**别在演示中途做**——重建要重新等 Hive 起来，一分半钟就没了。

**Q4｜七个容器怎么保证启动顺序？**
不是靠 `depends_on`，是靠 `condition: service_healthy`。区别是前者只等"容器起来"，后者等"健康检查通过"。各服务的健康检查间隔和 `start_period` 是分层给的：mysql 30 秒、metastore 60 秒、hive-server 和 superset 90 秒，冷启动越慢余量越大。

**Q5｜`app` 和 `api` 为什么是两个容器？不能合成一个？**
同一个镜像，两个入口。合成一个也行，但 Streamlit 是长连接会话型服务，API 是无状态短请求，混在一起互相拖累——大屏刷新会跟问答抢线程。分开之后，api 挂了不影响问答，问答重启也不影响大屏。

**Q6｜Superset 为什么有四个数据源？**
三个在用，一个是我调试时重复建的（全角括号 vs 半角括号），名下 0 数据集 0 图表。删一条 SQL 就行，但不在演示前动元数据库。

**Q7｜大屏那个"实时接口"，是每次刷新都去查 Hive 吗？**
不是。这一点我不绕：`/api/dashboard.json` 读的是 `export_dashboard_data.py` 从 Hive 导出的快照文件，按 mtime 做缓存，文件更新了才重载；只有接口拿不到时才回落到前端内嵌的 `dashboard.js`。做成读文件是因为大屏要"推开就亮"，全量查 Hive 要好几秒。页脚上那两个"数据时点 / 实时接口"标记就是用来交底的——它不会假装自己是最新到秒的。

**Q8｜大屏那个 8010 是哪个容器？**
**这个必须照实说：它不是容器。** 大屏是本地静态 HTML，我用 `python -m http.server 8010` 在宿主机上起的静态服务，页面再去 `fetch` api 容器（8000）的 JSON。之所以没做成容器，是因为它只有一个 HTML 文件加两个数据文件；要做也可以，加一个 nginx 服务十行配置，但那属于"为了对称而对称"，我选择不加。

重启命令（开机或关掉终端后要重新起）：

```bash
cd "D:/新建文件夹/ydsh_week1/dashboard/echarts"
python -m http.server 8010 --bind 127.0.0.1
```

起来之后浏览器开 `http://127.0.0.1:8010/`。别写成 `file://` 直接双击 HTML——那样页面能开，但取数请求的 Origin 是 null，接口虽然放开了 CORS，边缘情况下仍可能被浏览器拦；走 http 服务最稳。

**Q9｜这套东西能上生产吗？**
不能，差三样：没有 HTTPS 和反向代理、口令是 `.env` 明文（该上密钥管理）、单机没有副本。但这三件事都不影响"架构对不对"——四层分层的边界是对的，换掉部署方式不用改一行 SQL。

## 附 · 三处必须照实说的地方

答辩时最怕的不是有短板，是短板被当成谎话。下面三处如果被问到，按原话答，不要绕：

1. **大屏的 8010 静态服务不在 compose 里。** 是宿主机上手动起的进程，重启电脑就没了，重启命令见本篇 Q8。说"它是个临时静态服务"比说"它是个服务"安全。
2. **`/api/dashboard.json` 读的是导出快照，不是实时查 Hive。** 页脚上写着数据时点，主动说出来就是"取舍"，被问出来才像"糊弄"。
3. **Superset 有一条孤儿数据源。** 4 条记录、3 条在用。原因、影响、清理方式都能说清，就不是问题。

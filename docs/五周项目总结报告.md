## 摘要

本项目用五周时间，把 6 张共 11.4 万行的原始 CSV，做成了一套从贴源层到可视化大屏全链路打通的经营分析系统：Hive 四层数仓落库 **47 张表、366 个分区**；全站 GMV 在 15 个出口上收敛到同一个数 **36,116,687.06 元**；NL2SQL 问答在 30 条真实问句上 **30/30** 执行成功；经营大屏、Superset 驾驶舱、对话式问答三个入口同时可用；7 个容器一条 `docker compose up -d` 起全，端到端 67 项断言 **64 PASS / 0 FAIL / 3 WARN**。

比"做完了"更值得写进报告的，是五周里踩到的四类真实问题：

1. **口径问题**——同一个"销售额"，按订单实付算 3,611 万，按明细标价算 6.17 亿，差 17 倍。这不是技术问题，是治理问题，最后靠"指标卡 + 唯一取数表"解决。
2. **静默错误**——清洗时品类名带尾随空格，导致 0.97% 的 GMV 在关联时凭空消失，不报错、不对账根本发现不了。
3. **供给不足被误判成模型不行**——NL2SQL 报"列不存在"，查下去是 Prompt 只给了 14 张表，地域成品表压根没暴露给模型。
4. **修得过头的反向故障**——给校验器加严之后，把完全正确的窗口函数 SQL 拦了下来。校验器必须成对测：负例证明它拦得住错的，正例证明它不拦对的。

这份报告按任务书的五个子任务与六项评分维度组织，每一章的数字都来自仓库里的脚本输出或容器实测，可复现命令见附录 B。

## 一、项目概述

### 1.1 业务背景

云购生活是一家新零售企业，线上线下同时经营：4 种渠道（门店 / APP / 小程序 / PC 官网）成交、4 种支付方式结算、8 个一级品类、60 家门店分布在 15 个省级区域。

项目开始前，业务侧的真实困境不是"没有数据"，而是四件事：

| 困境 | 具体表现 | 量化 |
|---|---|---|
| 口径打架 | 运营按订单实付算销售额，商品按明细标价算，开会各说各的 | 6.17 亿 vs 3,611 万，**相差 17 倍** |
| 取数靠人 | 每次要数都要找数据组写 SQL | 平均等 **1～2 天** |
| 看板是死的 | Excel 截图发群里 | 看到的是**上周**的数 |
| 没人对账 | 报表数字和明细对不上，定位不到是哪一层出的问题 | 无法追溯 |

### 1.2 建设目标

任务书要求"全流程整合与端到端联调、系统文档、Git 审查、综合答辩"。落到可验收的层面，本项目设了四个目标：

| 目标 | 验收口径 | 达成情况 |
|---|---|---|
| 链路通 | 原始 CSV → ODS → DWD → DWS → ADS → 预测 → NL2SQL → 可视化 → 部署，一条命令复现 | ✅ 67 项断言 64 PASS / 0 FAIL |
| 口径唯一 | 同一指标在不同出口必须是同一个数 | ✅ 15 处 GMV 全部 36,116,687.06 |
| 取数变快 | 自然语言提问 30 秒内出结果 | ✅ 平均 5.2 秒（含一次大模型调用） |
| 可视可用 | 大屏、驾驶舱、问答三入口同时可用 | ✅ 6 图表 + 8 图表 + 对话页 |

### 1.3 范围边界

**做完了的**：数据导入与清洗、四层建模、KPI 体系、时间序列预测、NL2SQL、智能洞察、两套可视化、Docker 部署、压测与优化、完整文档与 Git 审查。

**明确没做的**（写清楚比含糊过去更专业）：

- 不做实时链路（本项目是 T+1 批处理，没有 Kafka / Flink）；
- 不做权限体系（单用户演示环境，未接 LDAP / RBAC）；
- 不做多年度同比（数据只有 2024 一年，无法区分"异常"与"季节规律"）；
- 未启用 HDFS（Hive 仓库落在本地卷，单机演示够用，生产要换）。

### 1.4 团队与分工

按任务书建议的四个角色配置，本项目由一人承担全部角色，因此**每个角色的产出都必须以文档形式留痕**，否则"一人多岗"会退化成"一人糊弄"。实际做法是：

## 二、总体方案

### 2.1 技术架构

系统由 7 个容器组成，分三层：存储与计算、服务、应用。

```
┌──────────────────────────────────────────────────────────────┐
│  应用层   经营大屏(8010)  Superset(8088)  Streamlit 问答(8501) │
│           静态 ECharts      BI 驾驶舱        NL2SQL 对话       │
├──────────────────────────────────────────────────────────────┤
│  服务层   API(8000)  FastAPI 指标接口 / dashboard.json         │
├──────────────────────────────────────────────────────────────┤
│  计算层   HiveServer2(10000)      ClickHouse(8123/9000)        │
│           Hive Metastore(9083)    列式加速，压测对照            │
├──────────────────────────────────────────────────────────────┤
│  存储层   MySQL(3307) 元数据 + Superset 元数据库               │
│           Hive 仓库（本地卷）  ODS/DWD/DWS/ADS 四层            │
└──────────────────────────────────────────────────────────────┘
```

7 个服务的实测状态（`docker ps`，2026-11-27 08:26）：

| 容器 | 端口 | 状态 | 作用 |
|---|---|---|---|
| ydsh-mysql | 3307 | healthy | Hive 元数据、Superset 元数据 |
| ydsh-hive-metastore | 9083 | healthy | 表结构元数据服务 |
| ydsh-hive-server | 10000 / 10002 | healthy | SQL 执行引擎 + Web UI |
| ydsh-clickhouse | 8123 / 9000 | healthy | 列式引擎，压测对照 |
| ydsh-superset | 8088 | healthy | BI 驾驶舱 |
| ydsh-app | 8501 | healthy | Streamlit 问答页 |
| ydsh-api | 8000 | healthy | 指标 API |

**关键设计**：`depends_on` 全部配 `condition: service_healthy`，不是 `Started`。原因是 Hive 从容器 `Up` 到真正能接 SQL 差约 90 秒——用 `Up` 判断会让 app 在 Hive 还没准备好时启动，然后连接失败。

### 2.2 技术选型与理由

| 层 | 选型 | 为什么选它 | 代价 |
|---|---|---|---|
| 存储 | Hive + ORC + SNAPPY | 与课程要求一致；ORC 列存压缩比高，分区裁剪有效 | 交互延迟秒级，不适合直接服务前端 |
| 元数据 | MySQL 8.0 | Hive Metastore 原生支持；同一实例兼作 Superset 元数据库 | 单点，未做高可用 |
| 加速 | ClickHouse | 同一份数据换引擎做对照，验证"引擎差异"而非"SQL 写法差异" | 需额外同步一次数据 |
| BI | Superset 4 | 开源、SQL Lab 可下钻、看板可分享 | 首次启动慢，需初始化元数据库 |
| 大屏 | ECharts（本地化 vendor） | 不依赖 CDN，断网可演示 | 手写 HTML，无可视化编辑器 |
| 问答 | Streamlit + 大模型 API | 交互轻、改一版不用重新打包前端 | 无并发设计，单用户演示 |
| 编排 | Docker Compose | 一条命令起 7 个服务，环境可复现 | 单机，未上 K8s |

**为什么不把大屏直接接 Hive**：Hive 单查询 P50 850.8ms，大屏 6 张图并发会互相排队。实际做法是导出快照 `dashboard/echarts/data/dashboard.json`，大屏读静态 JSON（带 mtime 缓存），刷新一次约 40ms。这是**用数据新鲜度换渲染速度**的显式取舍：T+1 场景下，快照和实时查 Hive 的结果本来就一样。

### 2.3 一个订单走完九站

报告后面所有数字，都可以用这一条链路串起来：

```
① CSV 落盘           data/*.csv（6 张，11.4 万行）
② ODS 贴源           ods_order 等 6 张，TEXTFILE，原样保留脏数据
③ 清洗               TRIM / CASE WHEN / 正则 / 去重 / 异常值剔除
④ DWD 明细           dwd_order 15,600→14,398 单，分区 dt
⑤ DWS 汇总           dws_trade_day / dws_store_day / dws_category_day
⑥ ADS 应用           ads_kpi_overview / ads_region_sales / ads_category_topn
⑦ 预测               ts_forecast.py，随机森林，MAPE 11.79%
⑧ NL2SQL             自然语言 → SQL → 校验 → 执行 → 自修复
⑨ 可视化             大屏 / Superset / Streamlit，三入口同源
```

第 ④ 站的 15,600 → 14,398 是本项目最关键的一次口径决策：**清洗不是"把脏数据改到能用"，而是"明确哪些数据不该进仓"**。剔除的 1,202 单全部有据可查（重复 600、负金额 310、超上限 292），剔除后 GMV 仍是 36,116,687.06，与明细表逐笔求和一致。

**任务书要求**：DWS/ADS 建设与 KPI 计算、时间序列分析与预测、大模型 API 接入与密钥管理、NL2SQL 构建、AI 智能洞察、Git 团队协同。

| 子任务 | 做法 | 交付物 | 实测证据 |

| 智能洞察 | 规则检测异常 → 维度分解归因 → 分段生成文字 | `docs/AI洞察报告.md`、`data/insight_result.json` | 366 天中 11 天异常（3.0%），8 个归因数字逐个核对正确 |
| Git 协同 | 功能分支 + PR + Review + Fork 全流程 | `docs/Git协同记录.md` | 5 个 PR 合并、2 个 Issue 关闭 |

**预测模型的选择口径要写清楚**，否则数字会被误读：

| 模型 | MAE（元） | MAPE | RMSE（元） |
|---|---|---|---|
| 基线-上周同日 | 18,723.73 | 18.91% | 23,644.10 |
| 基线-近 7 日均值 | 13,584.32 | 13.93% | 17,091.01 |
| 基线-近 14 日均值 | 12,747.87 | 13.19% | 16,506.05 |
| 线性回归 | 12,121.66 | **11.55%** | 16,703.37 |
| **随机森林（选用）** | **12,038.70** | 11.79% | **16,312.17** |

脚本按 **MAE** 选模型，随机森林胜出；按 MAPE 则是线性回归略优（11.55% vs 11.79%），两者差 0.24 个百分点，在 28 天测试集上属于噪声范围。相对"上周同日"基线，MAE 改善 **35.7%**。

但必须同时说清局限：STL 分解的季节强度 0.2183、趋势强度 0.0859，**趋势很弱**——这条序列本身接近"均值 + 周内波动 + 噪声"，残差标准差 15,782.69，占均值 15.99%。所以 MAPE 11.79% 已经是这套数据的天花板附近，再换模型收益有限。

**压测四组实验的结论**（`data/bench/bench_result.json`）：

| 实验 | 对照组 | 结果 | 结论 |
|---|---|---|---|
| 分区裁剪 | 全表 366 分区 vs 常量谓词 1 分区 | 1,325.5ms → 556.8ms | 裁剪掉 99.7% 的扫描量，提速 2.4 倍 |
| 分区键包函数 | `substr(order_date,1,6)` | 413.6ms，命中 0 分区 | 函数包住分区键会**全表扫**，写法要改成范围谓词 |
| MAPJOIN | 普通 JOIN vs `/*+ MAPJOIN(s) */` | 2,358.6ms vs 2,381.4ms | Hive 已自动转 MapJoin，手动 hint 无收益 |
| 三引擎 | Hive / ClickHouse / MySQL | 日粒度 777.5 / 6.6 / 1.8 ms | 差两个数量级，见下 |

**引擎对比必须限定条件**，否则容易得出"ClickHouse 快 200 倍"的错误结论：

| 引擎 | 并发 | 请求数 | P50 | P95 | QPS |
|---|---|---|---|---|---|
| Hive | 4 | 12 | 850.8ms | 1,247.7ms | 4.17 |
| ClickHouse | 8 | 40 | 7.1ms | 10.7ms | 924.83 |
| MySQL | 8 | 40 | 3.2ms | 5.9ms | 728.08 |

并发不同（4 vs 8），所以**只能按延迟比说约 120 倍**（850.8 ÷ 7.1），不能说 QPS 提升 220 倍。这个口径在报告和答辩里统一。

## 四、数据治理成果

### 4.1 五类脏数据：从 70,979 到 193

清洗不是"跑几个 `CASE WHEN`"，而是先给每一类问题定义"什么叫修好了"。本项目的口径是：

```
修复率 = (清洗前脏数据数 − 清洗后脏数据数) ÷ 清洗前脏数据数
```

按这个口径，五类的最终账是 99.73%。但真正值得写的是**每一类是怎么判定的**：

| 类别 | 典型样本 | 判定依据 | 处理策略 | 为什么不换一种做法 |
|---|---|---|---|---|
| 枚举不规范 | `gold` / `金卡` / `金卡会员` | 对照 6 个字段的规范值域 | `CASE WHEN` 映射到中文标准值 | 不用模糊匹配——`金卡` 与 `钻石卡` 编辑距离近，模糊匹配会错配 |
| 格式不统一 | `2024/11/05 15:49` | 正则 + 长度 | 换分隔符、补 `:0` | 不用 `to_date` 兜底——解析失败会静默置 NULL |
| 异常值 | `pay_amount = -310`、`age = 150` | 业务规则 + IQR 上界 11,356.33 | 负金额整单剔除；年龄按区间中位数填充 | 不 Winsorize——负金额没有业务解释，截断会造出不存在的订单 |
| 重复值 | 同一 `order_id` 两行 | 主键去重，保留 `order_time` 最晚的一条 | `ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY order_time DESC)` | 不 `DISTINCT` 整行——两行字段有细微差异，整行去重会都留下 |
| 缺失值 | 193 条空邮箱 | 字段是否业务必填 | 邮箱保留空值，电话/年龄按规则补 | 不造 pseudo-mail——假数据比空值更危险 |

### 4.2 口径统一：17 倍差怎么收敛的

项目开始时最大的问题不是脏数据，是"销售额"有两个算法：

| 口径 | 算法 | 结果 |
|---|---|---|
| 运营口径 | 订单实付金额求和 | 36,116,687.06 元（3,611 万） |
| 商品口径 | 明细 `quantity × price` 求和 | 约 6.17 亿 |

差 17 倍的原因不复杂：明细表是"标价 × 数量"，订单表是"实付金额"，中间有折扣、优惠、退款。两个数都对，但回答的不是同一个问题。

**解法不是"选一个"，而是"定义清楚 + 只留一个出口"**：

1. `docs/指标定义文档.md` 作为唯一口径来源，每个指标写清"计算口径 / 取数表 / 当前值"；
2. GMV 只允许从 `dws_trade_day.gmv` 取，其他层只能引用、不能重算；
3. 端到端脚本对每个出口逐一断言，全部必须等于 36,116,687.06。

端到端脚本里共 **15 条 GMV 断言**。下表是其中 8 条代表性路径：

| 出口 | 取数路径 | 结果 |
|---|---|---|
| DWD 明细求和 | `SUM(dwd_order.pay_amount)` | 36,116,687.06 |
| DWS 日汇总 | `SUM(dws_trade_day.gmv)` | 36,116,687.06 |
| DWS 月汇总 | `SUM(dws_trade_month.gmv)` | 36,116,687.06 |
| DWS 门店汇总 | `SUM(dws_store_day.gmv)` | 36,116,687.06 |
| DWS 渠道汇总 | `SUM(dws_channel_day.gmv)` | 36,116,687.06 |
| ADS KPI 宽表 | `ads_kpi_overview` 的 GMV 行 | 36,116,687.06 |
| ADS 区域分布 | `SUM(ads_region_sales.gmv)` | 36,116,687.06 |
| ADS 品类 TopN | `SUM(ads_category_topn.gmv)` | 36,116,687.06 |

**0.97% 的静默丢失**是这条链路上最难查的一次：品类名尾随空格导致 JOIN 匹配失败，GMV 少 349,609.44 元。修复后算术闭合：

```
35,767,077.49（8 个已知品类）
+   349,609.44（未知品类，显式单列）
+         0.13（浮点尾差）
= 36,116,687.06
```

第三行的 0.13 元不是笔误，是 DOUBLE 求和的浮点误差。报告里保留它，是因为**承认 1 毛 3 的误差，比假装 0 误差更可信**。

| 导入前预评估 | 建仓前 | 22 类问题、70,979 项，先量化再动手 | `docs/数据质量预评估表.xlsx` |

### 5.2 建模设计

**事实表**：`dwd_order` 以 `order_id` 为粒度，按 `dt` 分区，冗余了 `store_id / user_id / product_id` 三个外键，避免查询时反复 JOIN。

**维表**：用户、商品、门店、日期、渠道、支付方式、订单状态、会员等级。其中支付方式与订单状态是**编码维表**，作用是"把 PT01 翻译成微信支付"——不让前端看到编码，是这一层最直接的价值。

**分区策略**：`dwd_order` 按天分区，366 个分区。压测证明分区裁剪有效（1,325.5ms → 556.8ms），但也暴露一个坑：`substr(order_date,1,6)` 这种写法会让分区失效，必须改成 `dt BETWEEN '2024-06-01' AND '2024-06-30'`。

**为什么 DWS 要按五个视角各建一张**：日、周、月、门店、渠道的聚合粒度不同，如果只用一张"万能宽表"，要么冗余到无法维护，要么每次查询都要重新 GROUP BY。五张表各有明确的使用场景，代价是存储增加约 3 倍——在 3,600 万 GMV 的数据量级上可以接受。

## 六、AI 能力建设

### 6.1 NL2SQL 的四段式架构

```
问题
 ├─ ① Schema 注入：21 张表、138 个字段、中文语义，6,067 字符
 ├─ ② 大模型生成：21 条硬约束 + 6 个 few-shot + 选表指南
 ├─ ③ 静态校验：表名白名单 / 列归属 / 中文列名纠偏 / 时间范围 / 危险关键字
 └─ ④ 执行与自修复：失败把数据库报错原文回灌，最多重试 1 次
```

关键设计是**③必须在④之前**：Hive 编译一次约 700ms，把明显错误的 SQL 拦在编译前，既省时间，也避免"错误 SQL 打满日志"。

### 6.2 四轮真实故障：从"拦不住"到"拦错了"

这一节是本项目最有价值的部分。四次故障都不是"模型太笨"，而是**工程边界没画对**。

**第一轮：中文列名幻觉（4.6）**

问"销量最高的前 5 个品类"，模型写出 `SELECT \`一级品类\`, \`排名\` FROM ...`，Hive 报 `10004 Invalid column reference '排名'`。

根因：Schema 里每行是"列名 类型 // 中文说明"，模型把 `//` 后面的中文当成了列名。
修法：三层——Prompt 加对错对照示例；校验器建"中文注释 → 英文列名"的唯一映射做纠偏；报错信息附真实列名清单。

**第二轮：表没给全（4.7）**

问"广东省的销售额是多少"，模型把 `province` 挂在 `dws_trade_day` 上，报 `10004 Invalid column reference 'province'`。

`province` 是真列，只是不在那张表里。查下去发现两个洞：
- Prompt 只暴露 14 张表，地域成品表 `ads_region_sales` 压根没给模型；
- 校验器只核对"列名存不存在"，不核对"列属不属于这张表"。

修法：白名单补到 21 张、加选表指南、新增 `check_column_refs` 做列归属核对，报错时直接告诉模型"它只在哪张表"。

**第三轮：校验器拦错了（4.8）**

问"各支付方式的成交额占比"，模型写的 SQL 完全正确：

```sql
SELECT pay_type_code, SUM(pay_amount) AS total_gmv,
       SUM(pay_amount) / SUM(SUM(pay_amount)) OVER () AS gmv_ratio
FROM ydsh_dwd.dwd_order
GROUP BY pay_type_code
ORDER BY gmv_ratio DESC
```

被校验器拦下，理由是"`gmv_ratio` 不属于 `dwd_order`"。可 `gmv_ratio` 是 SELECT 里 `AS` 现定义的**别名**，`ORDER BY` 引用别名是标准写法——而它恰好是 `ads_region_sales` 的真列，正好落进"列存在但不在本次表里"的判定。

修法：`collect_aliases()` 收集 `AS` 定义的名字；表名白名单先排除 CTE 名；测试用例从 17 条扩到 35 条，**新增的大半是正例**。

**第四轮：三处不报错的静默错**

| 现象 | 错在哪 | 补的规则 |
|---|---|---|
| "取消了多少订单"自修复后多了 `WHERE dt LIKE '2024-06%'` | 全年 2,023 单缩成 6 月 159 单，页面照写"执行完成" | `check_time_scope`：问句无时间词却加日期过滤 → 拦 |
| "门店经营情况"写成 `SUM(aov)` | 客单价均值相加，算出 948,527 元/单 | 比率列不能 SUM，客单价重算 `SUM(gmv)/SUM(order_cnt)` |
| "6 月各品类卖了多少"没 GROUP BY | 返回 248 行日明细，用户要的是 9 行 | 粒度跟着问句走 + 三张日粒度表注明聚合方式 |

这四轮的共同结论：**校验器必须成对测**。负例证明它拦得住错的，正例证明它不拦对的。只测负例的校验器会越改越严，最后把正常提问全挡在门外，而单测还全绿。

### 6.4 智能洞察：先统计，后生成

很多"AI 洞察"的做法是把数据丢给模型让它说点什么，问题是模型不知道哪条是异常，只能说"整体平稳、需关注波动"；更糟的是编一个原因，而没人能验证。

本项目反过来：

```
规则检测异常 → 维度分解归因 → 分段生成文字
```

- **检测用规则**：偏离前 7 日均值 40% 以上。阈值不是拍脑袋——25% 会判出 78 天异常（21.3%），"五分之一的样本都异常"说明检测器有问题；50% 只剩 7 天，会漏真实异常；40% 得到 11 天（3.0%），且与 z>3 这条独立判据收敛到同一量级。
- **归因用分解**：把偏差拆到渠道和品类，算出各维度的金额贡献，每个数字可复算。
- **生成分段**：一次写 300～400 字模型想不完，拆成"整体表现 / 异常日分析 / 建议"三段各 100 多字，分别调用再拼接。

结果：366 天中 11 天异常（3.0%），Top 3 异常日全部为大幅上涨（+60%～+75%），摘要里 8 个归因数字逐个核对全部正确，无编造。

**必须说的局限**：这个数据集没有"营销活动"字段，所以无法验证异常是不是促销导致的。归因只能到"哪个渠道、哪个品类贡献了多少"，再往下就是猜。报告里写清这一点，比强行解释成"因为促销"要诚实。

### 6.5 对 AI 协同的批判性反思

| 认知 | 具体表现 |
|---|---|
| 模型不是越大越好，是**上下文越准越好** | 4.7 那次不是模型不会写 JOIN，是它看不到该 JOIN 的表 |
| 弱模型对**示例**的服从度高于对**规则**的服从度 | 城市维度写了 3 次规则都改不过来，加 1 条 few-shot 后一次通过 |
| 校验器要**成对测** | 只测负例会越改越严，最后把对的拦在门外 |
| AI 生成的内容必须**可核对** | 洞察摘要 8 个数字逐个核对，不允许出现无法复算的结论 |
| 报错信息的价值取决于**有没有"该去哪"** | 只说"列不存在"没用，要附"它只在哪张表" |

### 11.2 三条方法论

**第一，先看供给，再看模型。**
NL2SQL 报"列不存在"，第一反应容易是"模型不行、换个大的"。但 4.7 那次查下去是表没给全——模型看不到地域表，只能硬编。**上下文给对了，弱模型也能写对；上下文给错了，强模型也只能猜。**

**第二，能被对账的错才是好错。**
项目里最危险的不是报错的 SQL，是"执行完成、数字错了"的 SQL：取消单量从 2,023 变 159、客单价算出 94 万、品类汇总 248 行。这三类都不报错。解法不是"更小心"，是把对账做成断言——**层与层之间必须有数字闭合，闭合不上就失败**。

**第三，校验器要成对测。**
4.8 那次翻车，本质是只测了"该拦的拦住了"，没测"不该拦的放行了"。35 条用例里 12 条正例，就是为了守住这条线。这个道理不只适用于校验器：**任何"收紧"的改动，都要同时证明它没有伤到正常路径。**

### 11.3 个人收获

技术上最大的收获不是学会了 Hive 或 ECharts，而是理解了**"数据系统的一致性"是靠断言维持的，不是靠人记住**。项目里 15 个出口的 GMV 能对上，不是因为我每次都算对了，是因为脚本每次都会检查，不对就红。

工程上最大的收获是**知道了自己会在哪里偷懒**：改完代码直接 `docker cp` 不重建镜像、改完 Prompt 不回归全部问句、文档数字凭记忆写。这三件事各出过一次问题，现在都变成了流程里的固定动作。

表达上的收获来自答辩稿的写作：把 16 页 PPT 逐页写成口语稿，逼着自己回答"这一页到底想让听众记住什么"。写不出来，说明这页本来就没想清楚。

## 附录 C：术语表

| 术语 | 含义 |
|---|---|
| ODS | 贴源层，原样保留原始数据 |
| DWD | 明细层，清洗后的事实与维度 |
| DWS | 汇总层，按视角预聚合 |
| ADS | 应用层，直接服务报表与接口 |
| GMV | 成交总额，本项目口径为有效订单实付金额之和 |
| AOV | 客单价，GMV ÷ 订单量 |
| MAPE | 平均绝对百分比误差，预测评估指标 |
| 分区裁剪 | 查询只扫描命中分区的数据，避免全表扫 |
| MapJoin | 小表广播到各节点做 map 端连接 |
| few-shot | 在 Prompt 里给示例，让模型照着写 |
| 自修复 | 执行失败后把报错回灌给模型，让它改一版 |
| 静默错误 | 不报错但结果错的 SQL 或数据问题 |
